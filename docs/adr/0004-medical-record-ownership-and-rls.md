# 0004. Владение медзаписью и модель RLS

- Статус: Принято
- Дата: 2026-09-27

## Контекст

Медицинская запись принадлежит клинике (tenant): клиника — оператор данных
и отвечает за доступ к ним. Все клиники ячейки делят одну БД
(см. [0003](0003-cells-and-data-residency.md)). Одна пропущенная проверка
tenant в коде сервиса — утечка PHI другой клинике. Нужен второй рубеж,
который не зависит от правильности каждого запроса.

## Решение

**Два рубежа.** Первый — код сервиса: каждый запрос фильтрует по tenant.
Второй — Postgres Row-Level Security: даже если код ошибся, БД не отдаст
чужие строки.

**Роли БД** (`deploy/postgres/initdb/10-roles.sh`):

- `neurodent_owner` — владелец схем и таблиц, под ним работает только
  `cmd/migrate` (DDL);
- `neurodent_app` — роль API: только DML по явным грантам из миграций;
  не владелец таблиц (не может отключить RLS или изменить политики),
  `NOBYPASSRLS`, `NOSUPERUSER`, `NOINHERIT`.

**Tenant-таблица:**

- `ENABLE ROW LEVEL SECURITY` и `FORCE ROW LEVEL SECURITY` (FORCE
  распространяет политику и на владельца);
- политика `USING` и `WITH CHECK`:
  `tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`.
  Без tenant сравнение с NULL ложно — ноль строк. `NULLIF` нужен, потому
  что на соединении, где уже был `SET LOCAL`, параметр равен `''`, а не NULL;
- дополнительные политики — только `AS RESTRICTIVE`: permissive-политики
  объединяются через OR и могут ослабить изоляцию.

**Tenant-контекст:** `platform/postgres.DB.WithinTx` первым запросом
транзакции выполняет `set_config('app.tenant_id', id, true)` (это
`SET LOCAL`). Значение не переживает транзакцию и не протекает в следующий
запрос на том же соединении пула. Пул наружу не отдаётся: запрос мимо
`WithinTx` невозможен.

Каждое свойство доказано integration-тестом (`tests/integration`) и
ручной мутацией.

## Альтернативы

- **Только фильтр в коде.** Одна ошибка — утечка; проверить отсутствие
  ошибок во всех будущих запросах невозможно.
- **Схема или БД на tenant.** Сильнее изоляция, но тысячи схем и баз
  усложняют миграции и пулы (см. 0003).
- **Сессионный `SET app.tenant_id` при выдаче соединения из пула.** Значение
  переживает возврат в пул; забытый сброс = чужой tenant у следующего
  запроса. `SET LOCAL` в транзакции исключает этот класс ошибок.
- **BYPASSRLS для служебных задач приложения.** Не выдаём: межклиническая
  операция, если понадобится, — отдельный путь с отдельной ролью, аудитом
  и отдельным ADR.

## Последствия

- Любой доступ к данным — в транзакции; стоимость — `BEGIN` и `set_config`
  на запрос (микросекунды на фоне сетевого RTT).
- Миграции обязаны для каждой tenant-таблицы включать ENABLE + FORCE,
  политику и явные гранты. Шаблон — `migrations/0001_platform_rls_probe.sql`;
  проверка — integration-тест модуля.
- Кабинет пациента с записями в нескольких клиниках читает их по одной
  клинике за транзакцию, каждый раз со своим tenant-контекстом.
- Спроектировано по контролям: HIPAA 45 CFR §164.312(a)(1) (контроль доступа),
  §164.308(a)(4) (управление доступом к информации); GDPR ст. 25 и 32;
  ISO/IEC 27001:2022 A.8.3 (ограничение доступа к информации), A.8.2
  (привилегированный доступ); SOC 2 CC6.1.
