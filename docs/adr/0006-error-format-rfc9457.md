# 0006. Формат ошибок API: RFC 9457

- Статус: Принято
- Дата: 2026-09-27

## Контекст

Нескольким клиентам нужен единый машиночитаемый формат ошибок. Ошибки 5xx
не должны раскрывать внутреннее устройство (SQL-ошибки, имена таблиц,
фрагменты PHI), а поддержке нужно быстро находить запись в логе по жалобе
пользователя.

## Решение

- Все ошибки — `application/problem+json` (RFC 9457): `type` (всегда
  `about:blank`), `title` (текст статуса), `status`, `detail`, расширения
  `code` (машиночитаемая категория) и `request_id` (связь с логами).
- Приложение сообщает об ошибке через `shared/apperr`: категория
  (`invalid`, `not_found`, `conflict`, `unauthenticated`, `forbidden`,
  `rate_limited`, `unavailable`, `internal`), безопасное сообщение и
  внутренняя причина. Нулевая категория — `internal` (fail-safe).
- Маппинг категория → статус — в одном месте, `httpx.StatusOf`.
  `*http.MaxBytesError` в цепочке → 413 независимо от категории.
- Для 5xx `detail` всегда общий, причина — только в лог уровня error.
- Ошибки транспорта (404/405 роутера, 413, 503 таймаута, 500 паники)
  используют тот же формат.

## Альтернативы

- **Свой формат `{"error": {...}}`.** Ничем не лучше стандарта; клиентам и
  шлюзам приходится учить ещё один формат.
- **Сообщение ошибки как есть (`err.Error()`).** Утечка внутренних деталей
  и PHI в ответы.
- **Коды ошибок на каждый случай (`PATIENT_NOT_FOUND`).** Точнее, но
  раздувает контракт на старте; при необходимости добавляются как поле
  расширения без смены формата.

## Последствия

- Клиенты различают ошибки по `status` и `code`, а не по тексту.
- Любой код, создающий ошибку для клиента, выбирает категорию явно; забытая
  категория даёт 500 без деталей, а не утечку.
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.28 (безопасная
  разработка: обработка ошибок без раскрытия информации).
