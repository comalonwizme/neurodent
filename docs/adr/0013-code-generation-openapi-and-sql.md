# 0013. Кодогенерация: OpenAPI и SQL

- Статус: Принято (после ревью, 2026-09-27)
- Дата: 2026-09-27
- Связанные: 0002 (spec-first), 0006 (RFC 9457), 0007 (pgx), 0012 (шаблон модуля)

## Контекст

[0002](0002-spec-first-openapi.md) делает спецификацию OpenAPI источником
истины и откладывает генерацию до фазы 1. [0007](0007-postgres-driver-pgx.md)
оставляет открытым вопрос sqlc. Первый модуль не должен выбирать
инструменты сам.

Ограничения, которые генерация обязана сохранить:

- **тело запроса читает строгий `httpx.DecodeJSON`**: неизвестные поля —
  ошибка, `Content-Type: application/json` обязателен (CSRF-рубеж);
- **все ошибки — RFC 9457**, включая ошибки разбора параметров пути и
  query;
- **маршруты регистрируются на нашем `ServeMux`**: `routeProblems`
  (404/405) и access-лог (шаблон маршрута) работают через него;
- **границы модулей** ([0012](0012-module-template-and-cross-module-transactions.md)):
  сгенерированный код одного модуля не должен быть доступен другим.

## Решение

### OpenAPI → Go: oapi-codegen v2.8.0, std-http, не strict

- Спецификация — один файл `api/openapi/openapi.yaml`, OpenAPI **3.0.3**
  (основная версия, которую полностью поддерживает oapi-codegen).
  Каждая операция помечена тегом модуля: `platform` (health), `iam`,
  `org`, … Один файл — один документ для клиентов и ревью контракта.
- **Генерация по тегу** (`output-options.include-tags`): у каждого модуля
  свой пакет со своим `ServerInterface` и только своими моделями.
  - Код модуля лежит внутри модуля:
    `internal/modules/<m>/internal/adapters/http/api/`. Чужой модуль его
    импортировать не может — это `internal/` (запрещает компилятор).
  - Эндпоинты платформы: `internal/gen/platformapi/`.
- **`std-http-server: true`, не strict-server.**
  - Сгенерированный `HandlerWithOptions` регистрирует маршруты на
    переданный `ServeMux` (`BaseRouter`) шаблонами Go 1.22+
    (`GET /healthz`). Цепочка middleware, `routeProblems` и шаблоны в
    access-логе не меняются.
  - Тело запроса хендлер читает сам через `httpx.DecodeJSON`, ответ
    пишет через `httpx.WriteJSON` со сгенерированными типами.
  - Strict-server отпадает: он декодирует тело своим
    `json.NewDecoder` без `DisallowUnknownFields` и забирает у нас
    управление ответом.
- **Ошибки параметров** — через `ErrorHandlerFunc`.
  - oapi-codegen отдаёт типизированные ошибки (`InvalidParamFormatError`,
    `RequiredParamError`, … с `ParamName`). Наш обработчик пишет 400
    RFC 9457 с сообщением `parameter "id" is invalid`.
  - Сообщение строится **из имени параметра, а не из `err.Error()`**:
    текст runtime-библиотеки цитирует присланное значение. То же правило,
    что в `DecodeJSON`: значения из запроса клиенту не возвращаются.
- **Runtime-зависимость** — `github.com/oapi-codegen/runtime` v1.7.0,
  разбор параметров. Измерено на пробной сборке:
  - в бинарник попадают 3 модуля: runtime, `google/uuid`,
    `apapsch/go-jsonmerge`;
  - gin, echo и iris, объявленные в `go.mod` runtime, не линкуются, и
    pruning графа модулей не добавляет их в наш `go.mod`;
  - govulncheck проверяет их вместе с остальными.

### SQL → Go: sqlc v1.31.1

- `engine: postgresql`, `sql_package: pgx/v5`.
- Схема для sqlc — наши миграции `backend/migrations/*.sql`, отдельного
  файла схемы нет. Проверено: sqlc разбирает `0001` с RLS-политиками,
  `GRANT` и `uuidv7()`.
- Запросы лежат рядом с адаптером модуля
  (`internal/modules/<m>/internal/adapters/postgres/queries/*.sql`), код —
  там же (`…/adapters/postgres/sqlcdb/`). Для платформы (аудит, rate
  limit) — внутри своего пакета `platform/<pkg>/`.
- Сгенерированный `Queries` принимает `DBTX`. Его реализует `pgx.Tx` из
  `postgres.Tx(ctx)` (0012): `sqlcdb.New(tx)`.
- `uuid` в Postgres по умолчанию генерируется как `pgtype.UUID`. Маппинг
  на `shared/id` делается через `overrides`, если pgx корректно сканирует
  stdlib `uuid.UUID`. Иначе конвертация остаётся в адаптере. Проверяется
  в 0.7.4.

### Версии инструментов и запуск

- Инструменты объявлены директивой `tool` в **отдельном модуле**
  `backend/tools/go.mod`, запуск:

  ```bash
  go tool -modfile=tools/go.mod oapi-codegen …
  go tool -modfile=tools/go.mod sqlc generate
  ```

  Проверено: так основной `go.mod` не меняется. Зачем отдельный модуль:
  sqlc тянет свой pgx (v5.9.2), wazero и десятки пакетов. В общем `go.mod`
  минимальный выбор версий (MVS) связал бы версии прод-зависимостей с
  версиями инструментов.
- sqlc собирается с `CGO_ENABLED=0` (проверено), C-компилятор и Docker
  для генерации не нужны.
- `make generate` запускает все конфигурации oapi-codegen и `sqlc generate`.
- **Сгенерированный код коммитится.** `go build` не требует инструментов,
  а изменения контракта видны в диффе PR.
- Шаг CI «сгенерированный код актуален»:
  `make generate && test -z "$(git status --porcelain)"`. Не
  `git diff --exit-code`: он не видит новые неотслеживаемые файлы, например
  пакет нового модуля, который забыли закоммитить.
- **Линтеры.** golangci-lint по умолчанию пропускает файлы с маркером
  `Code generated … DO NOT EDIT.`, отдельные исключения по путям не нужны.
  Тест архитектуры (0012) сгенерированный код проверяет, потому что
  импорты имеют значение.

### Отличия от решения по умолчанию из ТЗ 0.7

- **Генерация по тегам в пакет внутри модуля**, а не общий `internal/gen/`
  для всех: иначе любой модуль мог бы импортировать DTO чужого API.
  `internal/gen/` остаётся для эндпоинтов платформы.
- **Инструменты в отдельном `tools/go.mod`**, а не `tool` в основном
  `go.mod` (см. MVS выше).
- **Проверка актуальности через `git status --porcelain`**, а не
  `git diff --exit-code`.

## Альтернативы

- **oapi-codegen strict-server.** Типизированные ответы по кодам статуса —
  сильная гарантия. Но декодирование тела без `DisallowUnknownFields`
  нарушает [0002](0002-spec-first-openapi.md) и 0.3, а обходить это
  пришлось бы на каждом эндпоинте.
- **ogen.**
  - Плюсы: строгий декодер и валидация по схеме; вариант при появлении
    сложных схем с `oneOf`.
  - Минусы: свой роутер (не `ServeMux` — `routeProblems` и шаблоны
    access-лога пришлось бы переписать), свой JSON-кодек и обязательная
    зависимость генерируемого кода от OpenTelemetry, хотя трассировка —
    вне рамок 0.7. Ради строгости, которая у нас уже есть в
    `DecodeJSON`, это много.
- **Один `ServerInterface` на всю спецификацию.** Модули реализуют части
  интерфейса, `internal/app` собирает их встраиванием структур. Проще
  конфигурация генерации, но общий пакет DTO доступен всем модулям, и
  границу держит только тест архитектуры, а не компилятор.
- **Отдельный файл спецификации на модуль** (`iam.yaml`, `org.yaml` плюс
  общий `common.yaml`). Та же изоляция, что у генерации по тегам, но
  клиентам нужен склеенный документ (ещё один инструмент), а `$ref`
  между файлами требует `import-mapping`.
- **Проверка запросов по спецификации в рантайме** (kin-openapi
  `openapi3filter`). Дублирует `DecodeJSON`, тяжёлая зависимость в
  прод-бинарнике.
- **Образ sqlc по digest в Docker.** Воспроизводимо, но требует Docker
  для генерации у каждого разработчика и в CI. Раз sqlc собирается без
  cgo, `tools/go.mod` проще.
- **Без sqlc (pgx руками).** Меньше инструментов, но опечатка в SQL или
  несовпадение типов всплывает в integration-тесте, а не при генерации.

## Последствия

- `/healthz` и `/readyz` переезжают на сгенерированный интерфейс
  `platformapi` (0.7.4). Ответы не меняются, существующие тесты роутера
  это проверяют.
- Не-strict сервер не гарантирует на компиляции, что хендлер отвечает
  кодами и схемами из спецификации. Кандидат на добавление: тест
  соответствия ответов спецификации (kin-openapi только в тестах) — в
  фазе 1, когда эндпоинтов станет больше двух.
- Проверки спецификации линтером (redocly или spectral) пока нет.
  Добавляется вместе с первым модулем, если контракт начнёт расти.
- Изменение API = изменение `openapi.yaml` + `make generate` + реализация.
  CI не пропустит спецификацию и код, разошедшиеся друг с другом.
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.25 (безопасный
  жизненный цикл разработки), A.8.28 (безопасная разработка), A.8.32
  (управление изменениями).
