# 0002. Spec-first OpenAPI

- Статус: Принято
- Дата: 2026-09-27

## Контекст

API потребляют Angular-клиент, мобильное приложение и Python AI-сервис.
Контракт должен ревьюиться до реализации: изменение поля в медзаписи
затрагивает несколько клиентов и аудит доступа к данным. Код-first
генерация спецификации из аннотаций делает спецификацию побочным продуктом,
который легко рассинхронизировать с реальным поведением.

## Решение

- Источник истины — спецификация OpenAPI в `api/openapi/`. Изменение API
  начинается с PR в спецификацию.
- Серверные интерфейсы и DTO генерируются из спецификации в
  `internal/gen/` (фаза 1). Хендлер реализует сгенерированный интерфейс,
  поэтому расхождение с контрактом — ошибка компиляции.
- Формат ошибок в спецификации — `application/problem+json` по RFC 9457
  (см. [0006](0006-error-format-rfc9457.md)).
- В фазе 0 генерации нет: эндпоинтов, кроме health, ещё нет.

## Альтернативы

- **Code-first (аннотации → спецификация).** Быстрее на старте, но
  спецификация отражает то, что написано в комментариях, а не то, что
  делает код; ревью контракта смешивается с ревью реализации.
- **gRPC/protobuf.** Сильные контракты, но браузерный клиент требует
  grpc-web или шлюз, а внешние интеграции клиник ждут HTTP/JSON.

## Последствия

- Контракт ревьюится отдельно и раньше кода; клиенты генерируют SDK из той
  же спецификации.
- Нужен инструмент генерации и проверка в CI, что сгенерированный код
  актуален (фаза 1).
- Строгий декодер (`httpx.DecodeJSON`, неизвестные поля — ошибка) и
  спецификация должны совпадать: дополнительные поля в запросе — нарушение
  контракта, а не «игнорируемый мусор».
