# 0012. Шаблон модуля и транзакции между модулями

- Статус: Предложено
- Дата: 2026-09-27
- Связанные: 0001 (модульный монолит), 0004 (RLS), 0011 (субъект транзакции)
- Изменяет: механизм передачи tenant из [0004](0004-medical-record-ownership-and-rls.md)
  («tenant из контекста» → явный scope). Модель RLS из 0004 остаётся в силе.

## Контекст

[0001](0001-modular-monolith.md) задаёт модули и правило «только через
contract», но не говорит:

- как модуль устроен внутри;
- кто проверяет правила зависимостей;
- что происходит, когда use case одного модуля вызывает контракт другого
  внутри транзакции.

Текущий `WithinTx` берёт tenant из контекста неявно. Забытый
`tenant.WithID` не падает, а молча даёт «ноль строк». Для чтения это
fail-closed, но для записи в `cell-global` таблицу такая ошибка просто
незаметна.

## Решение

### 1. Раскладка модуля

```
internal/modules/<name>/
  module.go        конструктор модуля: New(Deps) — единственное, что видит internal/app
  contract/        интерфейсы и DTO для других модулей; только stdlib + shared/*
  internal/
    domain/        агрегаты, value objects, доменные ошибки; только stdlib (без I/O) + shared/*
    app/           use cases; открывают транзакции со scope
    ports/         интерфейсы репозиториев и внешних сервисов
    adapters/
      postgres/    реализация ports; sqlc-код модуля лежит здесь же
      http/        хендлеры; реализуют сгенерированный интерфейс модуля (0013)
```

`internal/` внутри модуля — не формальность. Компилятор Go запрещает
импортировать `modules/<name>/internal/...` из-за пределов
`modules/<name>/`. Половину правил границ держит сам язык, остальное —
тест архитектуры (п. 2).

DTO контракта — свои типы, не доменные. Иначе чужой модуль начинает
зависеть от внутренней модели, и рефакторинг домена ломает соседей.

### 2. Правила зависимостей проверяет тест

Тест `tests/arch` на stdlib (`go/parser`, режим `ImportsOnly`, плюс AST
для вызовов). Проверяются импорты всех `.go` файлов, включая файлы под
build-тегами:

| Пакет | Может импортировать | Не может |
|---|---|---|
| `modules/B/contract` | stdlib, `shared/*` | pgx, `net/http`, `platform/*`, свой `internal/*` |
| `modules/B` (module.go) | свой `internal/*`, всё нужное для wiring | — (импортируется только `internal/app`) |
| `modules/B/internal/domain` | stdlib без I/O, `shared/*` | pgx, `net/*`, `database/*`, `os/*`, `log/*`, `platform/*`, `app`, `adapters` |
| `modules/B/internal/app`, `ports` | `domain`, `ports`, `shared/*`, `modules/A/contract` | pgx, `net/http`, `platform/*`, `adapters/*` |
| `modules/B/internal/adapters/postgres` | pgx, `platform/postgres`, `domain`, `ports` | `adapters/http`, `net/http` |
| `modules/B/internal/adapters/http` | `net/http`, `platform/httpx`, сгенерированный API модуля, `app`, `domain` | `adapters/postgres`, pgx |
| `modules/A/...` → `modules/B/...` | только `modules/B/contract` | всё остальное |
| `platform/*`, `shared/*` | — | `modules/*` |
| `shared/*` | stdlib, `shared/*` | всё остальное |

Дополнительно проверяются два правила:

- **Граф модулей ацикличен.** Импорты `modules/A/**` → `modules/B/contract`
  образуют граф, цикл — ошибка. Ожидаемое направление первых модулей —
  `org` → `iam` (0011).
- **Вызовы `time.Now`, `time.Since`, `time.Until` запрещены** в `domain/`
  и `app/`: время только через `shared/clock` (п. 6).

Тест проверяет себя на фикстурах `tests/arch/testdata/<нарушение>/`. Это
файлы-нарушители, которым не нужно компилироваться: парсятся только
импорты. На каждое правило есть фикстура, и тест ждёт от неё ровно
ожидаемое нарушение.

### 3. Транзакция открывается с явным scope

Типы scope — в `internal/shared/scope`, без pgx. Их используют и use cases
(им нельзя импортировать `platform/*`), и `platform/postgres`.

```go
scope.Tenant(clinicID, scope.Staff(userID))
scope.Tenant(clinicID, scope.Patient(userID, patientID))   // userID — кто действует (может быть опекун)
scope.Tenant(clinicID, scope.System())
scope.Global(scope.User(userID))                           // пользователь вне клиники: профиль, сессии
scope.Global(scope.Anonymous())                            // до аутентификации: регистрация, вход
scope.Global(scope.System())
```

- Scope без actor не существует: журналу аудита
  ([0014](0014-audit-log.md)) нужен субъект **каждого** события, включая
  вход и регистрацию.
- В tenant-scope допустимы `staff`, `patient`, `system`; в global —
  `user`, `anonymous`, `system`. Остальные сочетания, нулевой scope,
  нулевой tenant и пациент без `patientID` — ошибка `WithinTx` до `BEGIN`.
  Забытый scope падает громко.
- `WithinTx` выставляет `SET LOCAL` параметры из 0011 (`app.tenant_id`,
  `app.actor_kind`, `app.actor_id`, `app.patient_id`).

Где открывается транзакция:

- **Use case** (точка входа из HTTP или фоновой задачи) открывает
  транзакцию: `WithinTx(ctx, scope, func(ctx) error)`.
- **Репозитории и реализации контрактов транзакций не открывают.** Они
  берут текущую из контекста: `postgres.Tx(ctx)`. Если её нет —
  `ErrNoTx`. Так вызов контракта вне транзакции невозможен.

### 4. Контракт другого модуля присоединяется к текущей транзакции

Транзакция лежит в контексте (ключ не экспортирован из `platform/postgres`).
Контракт принимает только `ctx`, pgx он не видит. Сгенерированные sqlc
запросы получают `pgx.Tx` из `postgres.Tx(ctx)` в адаптере.

Вложенный `WithinTx` при уже открытой транзакции:

- **тот же scope** — присоединяется через `SAVEPOINT`, то же соединение.
  Savepoint нужен из-за особенности Postgres: после любой ошибки SQL вся
  транзакция в состоянии `aborted`, и следующие запросы падают. С
  savepoint внешний use case может обработать ошибку вложенного вызова
  (например, `unique_violation` → «уже участник») и продолжить;
- **другой scope** — `ErrScopeMismatch`. Смена tenant или субъекта внутри
  транзакции — всегда ошибка логики.

Счётчики rate limit ([0016](0016-rate-limiting-and-trusted-proxies.md)) и
события отказа в аудите ([0014](0014-audit-log.md)) пишутся **вне**
бизнес-транзакции. Их откат вместе с ней потерял бы факт попытки.
Поэтому такие записи вызываются до `WithinTx` или после её завершения.

**Внутри транзакции нет сетевого I/O**: SMS, HTTP, AI-сервис. Транзакция
держит соединение и блокировки; внешний вызов на секунды исчерпает пул.

### 5. Идентификаторы генерирует приложение

`internal/shared/id` — обёртка над stdlib-пакетом `uuid` (Go 1.27,
`uuid.NewV7()`, монотонный). Новой зависимости нет.

Id нужен до INSERT: для события аудита, ответа клиенту и идемпотентности.
`DEFAULT uuidv7()` в таблицах остаётся как страховка.

Модули объявляют типизированные id (`type UserID id.ID`), чтобы
компилятор не дал передать id клиники вместо id пользователя.

### 6. Время — через `shared/clock`

```go
type Clock interface{ Now() time.Time }
```

- `clock.Real()` возвращает UTC.
- `clock.Manual` (для тестов) умеет `Set` и `Advance`.
- `time.Now()` в `domain/` и `app/` запрещён тестом архитектуры (п. 2).

### 7. Внешних ключей между схемами разных модулей нет

Внешних ключей между схемами разных модулей нет: модуль владеет схемой
([0001](0001-modular-monolith.md)). Целостность между модулями обеспечивает
оркестрация в одной транзакции (п. 4).

### Отличия от решения по умолчанию из ТЗ 0.7

| Было в ТЗ | Предлагаю | Почему |
|---|---|---|
| Scope в `platform/postgres` (`postgres.Tenant(id, actor)`) | Scope в `shared/scope` | use cases не могут импортировать `platform/*` |
| `Global()` без субъекта | `Global(actor)` | аудиту нужен субъект каждого события |
| Вложенный вызов с тем же scope — просто присоединение | Присоединение через `SAVEPOINT` | см. п. 4 |
| — | «Кто открывает транзакцию» (use case, а не репозиторий или контракт) | — |
| — | Запрет сетевого I/O в транзакции | — |
| — | Ацикличность графа модулей | — |
| `golang.org/x/tools/go/packages` или `go list` | Тест на `go/parser` | фикстурам не нужно компилироваться, новой зависимости нет |
| `shared/id` на своём коде | Stdlib `uuid` из Go 1.27 | уже есть в стандартной библиотеке |

## Альтернативы

**Передача транзакции явно:** `contract.Do(ctx, tx, …)`, где `tx` —
непрозрачный интерфейс.

- Плюсы: честно, ничего скрытого.
- Минусы: каждый контракт и use case тащит параметр транзакции; понятие
  «хранилище» протекает во все сигнатуры. Непрозрачный `Tx` без методов
  всё равно разворачивается в pgx внутри адаптера, то есть та же магия,
  но с шумом.

**Запрет межмодульных транзакций + outbox и события.**

- Плюсы: лучшая изоляция, готовность к выносу модуля в сервис.
- Минусы: «клиника + членство основателя» превращается в сагу с
  компенсацией. Для монолита это сложность без выгоды. Outbox нужен и
  так, но для уведомлений и интеграций, а не вместо транзакций (вне рамок
  0.7).

**Unit of Work, передаваемый явно.** Тот же компромисс, что у явной
транзакции, плюс собственный жизненный цикл объекта.

**Присоединение без savepoint.**

- Плюсы: на один round-trip меньше.
- Минусы: ошибка вложенного вызова необратимо «отравляет» транзакцию
  (см. п. 4).

**depguard в golangci-lint вместо своего теста.** depguard хорошо
выражает «пакеты X не импортируют Y». Но он не выражает правило «модуль A
импортирует модуль B только через `B/contract`» для произвольных A ≠ B
без перечисления всех пар, не проверяет ацикличность и `time.Now`.

**Интерфейсы портов в пакете `app` (Go-идиома «интерфейс у потребителя»)
вместо `ports/`.**

- Плюсы: на пакет меньше.
- Минусы: адаптеры тогда косвенно зависят от пакета use cases, и правило
  «адаптер не видит use cases» не выразить.

## Последствия

- Новый модуль начинается с каталога по шаблону и wiring в
  `internal/app`; `platform/*` и `app/*` не трогаются.
- `WithinTx` меняет сигнатуру:

  ```go
  WithinTx(ctx, scope.Scope, func(ctx context.Context) error) error
  ```

  `shared/tenant` теряет функции контекста (`WithID`/`FromContext`),
  тип `tenant.ID` остаётся. Существующие integration-тесты переводятся на
  scope и должны остаться зелёными.
- Контракт — долгоживущий интерфейс между командами. Изменение контракта
  ревьюится как изменение публичного API.
- UUIDv7 раскрывает время создания (48 бит миллисекунд). Для id,
  видимых наружу, это допустимо. Если время создания сущности окажется
  чувствительным, для неё можно выбрать `uuid.NewV4()`.
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.27 (принципы
  безопасной архитектуры), A.8.28 (безопасная разработка).
