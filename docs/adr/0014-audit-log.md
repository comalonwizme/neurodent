# 0014. Журнал аудита

- Статус: Предложено
- Дата: 2026-09-27
- Связанные: 0004 (RLS), 0011 (субъект транзакции), 0012 (scope, `shared/id`, `shared/clock`)

## Контекст

HIPAA требует механизмов, которые записывают и позволяют исследовать
активность в системах с ePHI. Расследование инцидента начинается с
вопросов:

- кто;
- в какой клинике;
- что сделал или пытался сделать;
- с каким ресурсом;
- когда;
- чем закончилось.

Журнал не должен сам становиться источником утечки: в нём не место PHI и
свободному тексту. Приложение не должно уметь его переписать.

Первый модуль (IAM) пишет события с первого эндпоинта, поэтому механизм
нужен до него.

## Решение

### Таблица `audit.events` (класс `audit`)

| Поле | Тип | Откуда |
|---|---|---|
| `id` | uuid | `shared/id`, генерирует приложение |
| `occurred_at` | timestamptz | `shared/clock`: когда произошло |
| `recorded_at` | timestamptz, `DEFAULT now()` | часы БД: когда записано; расхождение с `occurred_at` видно |
| `tenant_id` | uuid, NULL | из scope транзакции; NULL — событие вне клиники (вход, регистрация) |
| `actor_kind` | text | из scope: `staff`, `patient`, `user`, `anonymous`, `system` |
| `actor_id` | uuid, NULL | из scope; NULL для `system` и `anonymous` |
| `action` | text | стабильный код `<модуль>.<ресурс>.<глагол>`: `iam.session.created`, `emr.record.viewed` |
| `resource_type` | text | код типа: `iam.session`, `emr.record` |
| `resource_id` | uuid, NULL | идентификатор ресурса |
| `outcome` | text | `success`, `denied`, `failed` |
| `request_id` | text, NULL | из контекста запроса (`httpx.RequestID`) |

CHECK-ограничения в БД — второй рубеж к проверкам в Go:

- `action` совпадает с шаблоном `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*){2}$`;
- `resource_type` — тот же формат с двумя сегментами;
- `actor_kind` и `outcome` — из перечня;
- `request_id` — алфавит и длина из middleware request-id.

### Никакого PHI и свободного текста — это обеспечивают типы

В Go-API события нет ни одного поля «строка по выбору вызывающего»:

```go
type Event struct {
    Action       audit.Action       // код, проверяется форматом
    ResourceType audit.ResourceType // код, проверяется форматом
    ResourceID   id.ID              // UUID: имя или диагноз в него не положить
    Outcome      audit.Outcome      // перечисление
}
```

Tenant, субъект, время и `request_id` вызывающий **не передаёт** —
`Recorder` берёт их из scope транзакции, `clock` и контекста. Подделать
субъект или клинику события из кода модуля нельзя.

### Права и RLS

- Прикладной роли — **только `INSERT`**: без `SELECT`, `UPDATE`, `DELETE`,
  `TRUNCATE`. Id генерирует приложение, поэтому `INSERT … RETURNING`
  (которому нужен `SELECT`) не требуется.
- ENABLE + FORCE RLS.
  - `WITH CHECK` на вставку согласован со scope транзакции (0011):
    `tenant_id`, `actor_kind` и `actor_id` события совпадают с
    `platform.current_*()`. Даже SQL в обход `Recorder` не запишет событие
    от имени чужой клиники или чужого субъекта.
  - Политика `SELECT` по tenant заложена сразу — для будущей роли чтения.
- Чтение журнала — отдельным путём позже: роль, интерфейс для клиники,
  экспорт.

### Когда событие пишется

**Успешное действие — в той же транзакции, что и действие**
(`audit.Record(ctx, ev)` берёт транзакцию из контекста, 0012). Нет
действия без записи и записи без действия. Если запись в журнал не
удалась, действие откатывается.

**Отказ и сбой — отдельной транзакцией после отката.** Бизнес-транзакция
при `denied` или `failed` откатывается, и событие внутри неё пропало бы.
А именно эти события — попытки доступа к чужим данным, неудачные входы —
важнее всего при расследовании. Их пишет
`audit.RecordOutcome(ctx, scope, ev)` в собственной транзакции, вне
бизнес-транзакции (правило «вне транзакции» — 0012).

**Чтение PHI — тоже событие** (`emr.record.viewed`). Оно пишется в той же
транзакции, что и чтение: не записали — ответ не отдаётся. Поэтому
транзакции чтения PHI не могут быть `READ ONLY`.

### Отличия от решения по умолчанию из ТЗ 0.7

| Было в ТЗ | Предлагаю | Почему |
|---|---|---|
| Событие только в той же транзакции | Плюс отдельный путь для `denied` и `failed` | см. «Когда событие пишется» |
| — | Tenant и субъект — из scope, а не из аргументов | — |
| `WITH CHECK` по tenant | `WITH CHECK` по субъекту тоже | — |
| — | CHECK-ограничения формата кодов в БД | — |
| — | Поле `recorded_at` | — |
| `resource_id` любого типа | `resource_id` — UUID | свободный текст в нём невозможен |

## Альтернативы

- **Событие всегда в отдельной транзакции** (или асинхронно через
  очередь). Не теряет отказов, но появляются записи о действиях, которые
  откатились, и действия без записей, если процесс упал между шагами.
  Для успешных изменений ePHI атомарность важнее.
- **Журнал в логах приложения (slog → сборщик).** Дёшево, но логи
  изменяемы и неполны (sampling, потери при сбое сборщика), не
  транзакционны с действием и не защищены RLS.
- **Внешняя система аудита** (SIEM, append-only хранилище) как основной
  приёмник. Правильная цель для неизменяемости, но синхронная запись
  туда — сетевой I/O внутри транзакции (запрещено в 0012). Путь — экспорт
  из `audit.events` (см. ниже).
- **Поле «детали» (jsonb) для гибкости.** Первое, куда попадут PHI и
  свободный текст. Если контекст действительно нужен, это новое
  типизированное поле с кодом, через ревью этого ADR.

## Последствия

- Каждое изменение и чтение ePHI — это один `INSERT` в
  `audit.events`. Объём растёт быстрее данных, поэтому понадобится
  партиционирование.
- Владелец схемы (миграции) может изменить журнал: на `TRUNCATE` RLS не
  действует, а `UPDATE` и `DELETE` доступны владельцу по праву владения.
  Защита от подделки привилегированным пользователем — только
  hash-цепочка или внешний экспорт (ниже).
- Для IAM: события входа пишутся с `actor_kind = anonymous` до
  аутентификации и `user` после.

**Не сейчас** (записать в «что можно иначе» 0.7):

- партиционирование по времени (`occurred_at`, помесячно);
- hash-цепочка (`prev_hash`) для обнаружения подделки;
- экспорт во внешнее неизменяемое хранилище;
- роль и API чтения для клиники;
- срок хранения — решение с юристом;
- IP-адрес в событиях входа: полезен для расследования, но это
  персональные данные ([0016](0016-rate-limiting-and-trusted-proxies.md)),
  решается в ТЗ IAM.

Спроектировано по контролям:
- HIPAA 45 CFR §164.312(b) (аудит), §164.308(a)(1)(ii)(D) (обзор
  активности информационной системы);
- ISO/IEC 27001:2022 A.8.15 (журналирование), A.8.16 (мониторинг);
- SOC 2 CC7.2.
