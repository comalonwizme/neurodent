# 0001. Модульный монолит

- Статус: Принято
- Дата: 2026-09-27

## Контекст

NeuroDent покрывает много доменов: медзапись (EMR), расписание, CRM, склад,
финансы, кабинет пациента, AI-ассистент. Команда небольшая, система должна
жить десятилетиями, а границы доменов на старте известны не до конца. Данные
медицинские (PHI): каждое сетевое взаимодействие между компонентами —
дополнительная поверхность атаки, шифрование и аудит.

## Решение

Один Go-бинарник (`backend/cmd/api`), внутри — модули с жёсткими границами:

- модуль живёт в `internal/modules/<name>/` и общается с другими только через
  свой `contract/` (интерфейсы и DTO). Остальное скрыто пакетом `internal/`
  модуля — барьер держит компилятор, а не договорённость;
- модуль владеет своей схемой БД (`iam.*`, `org.*`, …). JOIN между схемами
  разных модулей нет: нужны чужие данные — вызов через contract;
- сквозная инфраструктура — в `internal/platform/*` (БД, HTTP, логи),
  общие примитивы без бизнес-логики — в `internal/shared/*`;
- зависимости собираются только в `internal/app` (composition root).

## Альтернативы

- **Микросервисы.** Независимый деплой и масштабирование ценой сетевых
  вызовов, распределённых транзакций, отдельного шифрования и аудита
  межсервисного трафика и операционной нагрузки, непосильной малой команде.
  Ошибка в границах сервисов стоит дорого: границы исправляются миграцией
  данных между базами.
- **Монолит без модульных границ.** Быстрый старт, но через пару лет —
  связность «всё со всем», JOIN'ы через домены и невозможность вынести модуль.

## Последствия

- Один деплой, одна транзакционная БД, простая локальная разработка.
- Границы проверяет компилятор; ошибку границ исправляют рефакторингом
  внутри одного репозитория.
- Модуль с отдельной схемой и контрактом можно вынести в сервис позже, если
  появится реальная причина (нагрузка, отдельный цикл релизов).
- Запрет JOIN между схемами требует дисциплины: отчёты через несколько
  доменов строятся через контракты или отдельные read-модели.
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.27 (принципы безопасной
  архитектуры), A.8.28 (безопасная разработка).
