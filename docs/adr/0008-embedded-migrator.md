# 0008. Миграции: свой мигратор на go:embed

- Статус: Принято
- Дата: 2026-09-27

## Контекст

Схема меняется миграциями от роли-владельца (см. [0004](0004-medical-record-ownership-and-rls.md)).
Каждая ячейка мигрируется независимо (см. [0003](0003-cells-and-data-residency.md)).
Требования: миграции внутри бинарника (версия схемы привязана к версии кода),
атомарность, защита от параллельного запуска, обнаружение изменённых
миграций, безопасность для работающего API.

## Решение

Свой мигратор (`internal/platform/postgres/migrate.go`, `cmd/migrate`,
~150 строк):

- файлы `migrations/NNNN_name.sql`, встроены через `go:embed`; версии идут
  подряд с 0001, неверное имя `.sql` — ошибка, а не пропуск;
- каждая миграция и запись о ней в `public.schema_migrations` — одна
  транзакция: применена целиком или не применена;
- `pg_advisory_lock` — два мигратора не работают одновременно;
- sha256 содержимого: изменённая после применения миграция — ошибка;
- БД новее бинарника (неизвестная применённая версия) — ошибка;
- `SET LOCAL lock_timeout = '5s'`: DDL, ждущий `ACCESS EXCLUSIVE`, не
  ставит в очередь весь трафик API к таблице — миграция падает и
  повторяется;
- только вперёд: откат медицинских данных — новая миграция, а не
  down-скрипт.

## Альтернативы

- **golang-migrate, goose, atlas.** Зрелые инструменты, но тянут
  зависимости (драйверы нескольких СУБД, облачные источники), а нужные нам
  свойства (lock_timeout в каждой миграции, отказ при «БД новее кода»,
  контрольные суммы) либо отсутствуют, либо требуют настройки. Объём
  своего кода мал и полностью покрыт тестами.
- **Миграции при старте API.** У роли API нет прав на DDL (это часть
  модели безопасности); кроме того, N реплик стартуют одновременно.

## Последствия

- Нет down-миграций: ошибочная миграция исправляется новой.
- `CREATE INDEX CONCURRENTLY` нельзя выполнить в транзакции; понадобится
  директива «без транзакции» — добавим вместе с первой такой миграцией.
- Поддержка мигратора — наша ответственность; поведение зафиксировано
  unit- и integration-тестами (идемпотентность, параллельный запуск,
  контрольные суммы, откат упавшей миграции).
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.32 (управление
  изменениями), A.8.9 (управление конфигурацией); SOC 2 CC8.1.
