# 0019. Клиентские приложения и платформы

- Статус: Принято (после ревью, 2026-09-28)
- Дата: 2026-09-28
- Связанные: 0002 (spec-first), 0003 (резидентность), 0011 (идентичность), 0013 (кодогенерация), 0017 (сессии), 0018 (CORS и CSRF)

## Контекст

Изначально предполагалось одно Angular-приложение на `app.<домен>`. Но у
продукта две аудитории с разными задачами:

- **Пациент** пользуется телефоном: записи, планы лечения, оплаты,
  напоминания. Ему нужно приложение из стора.
- **Персонал** работает в основном за компьютером и планшетом у кресла:
  расписание, медкарта, склад. Врачу и основателю нужен и телефон:
  расписание на день, фото зубов в запись, дашборд, одобрения.

Аккаунт у человека один (0011): каждый — пациент, роли в клиниках
добавляются к этому статусу.

Этот ADR фиксирует, какие клиенты существуют, на каких платформах и
доменах, и какие ограничения безопасности из этого следуют.

## Решение

### 1. Два приложения, один аккаунт

| Приложение | Аудитория сессии (0017) | Веб | iOS / Android | Десктоп |
|---|---|---|---|---|
| **NeuroDent** | `patient` | минимальный: вход, записи | основная платформа | — |
| **NeuroDent Clinic** | `clinic` | основная платформа | да, включая планшеты | устанавливаемый PWA |

- Приложение клиники показывает экраны по роли участника в выбранной
  клинике.
- Переход между приложениями — handoff (0017, п. 7). В профиле пациента
  кнопка перехода видна, только если у пользователя есть членство в
  клинике или платформенная роль.
- **Нативное десктоп-приложение** (Tauri или Electron) не делаем. Оно
  понадобится, только если нужна работа с оборудованием: визиограф,
  фискальный регистратор, платёжный терминал. Решение принимают ADR по
  фискализации и по снимкам.

### 2. Один код: Angular workspace и Capacitor

```
web/
  apps/
    patient/        NeuroDent: веб + Capacitor
    clinic/         NeuroDent Clinic: веб + Capacitor
  libs/
    ui/             дизайн-система, общие компоненты
    api-client/     сгенерирован из api/openapi/openapi.yaml
    auth/           вход, handoff, оба транспорта сессии
    i18n/           ru, kk, en; RTL-ready
```

- Мобильные сборки — Capacitor. Это то же Angular-приложение в WebView
  плюс плагины к нативным API: push, камера, биометрия, защищённое
  хранилище.
- `libs/auth` скрывает транспорт от остального кода: в вебе — cookie, в
  оболочке — bearer из Keychain/Keystore. Остальной код не знает, где
  работает.
- TypeScript-клиент генерируется из **той же** спецификации, что и
  Go-сервер (0013). Инструмент выбирается в ТЗ 1.7. ADR-0013 не меняется:
  спецификация остаётся единственным источником контракта.

### 3. Домены

| Хост | Что |
|---|---|
| `<домен>` (apex) | маркетинговый лендинг, статический, без фреймворка |
| `clinic.<домен>` | веб NeuroDent Clinic |
| `my.<домен>` | веб NeuroDent |
| `api.<домен>` | Go API |

- Все хосты — один site, поэтому cookie `SameSite=Strict` на `api.`
  работают для обоих веб-приложений (0017).
- `app.<домен>` не используется.
- На лендинге нет сессий, и он не входит в списки origin API (0018).
  Взлом лендинга не даёт доступа к API.

### 4. Группы маршрутов API

```
/v1/auth/...                            вход, handoff, выход
/v1/clinic/...                          персонал; данные клиники — /v1/clinic/clinics/{clinicId}/...
/v1/me/...                              пациент
```

- Группа определяет допустимую аудиторию сессии (0017, п. 2).
- Теги OpenAPI по-прежнему означают модули (0013). Группа маршрутов —
  это префикс пути и схема безопасности операции, а не тег.

### 5. Ссылки в приложения: только проверенные по домену

- Universal Links (iOS) и App Links (Android) на путь `/auth/handoff`
  хостов `clinic.` и `my.`.
- Файлы проверки `/.well-known/apple-app-site-association` и
  `/.well-known/assetlinks.json` отдаёт статика соответствующего хоста.
  В файлах перечислен только этот путь.
- Свои URL-схемы (`neurodent://`, `neurodentclinic://`) запрещены: на
  Android их может зарегистрировать и перехватить любое приложение.

### 6. Push-уведомления — исключение из правила «данные не покидают регион»

По 0003 PHI не покидает регион ячейки, а внешние API по умолчанию
запрещены. Push физически доставляется только через Google (FCM) и Apple
(APNs), и обойти их нельзя. Исключение допускается при условиях:

- **В payload нет PHI и персональных данных.** Только тип уведомления из
  закрытого перечня, локализованный общий текст без параметров («У вас
  новое напоминание») и непрозрачный идентификатор. Имени пациента,
  врача, клиники, диагноза, суммы в push нет.
- Содержание приложение загружает через API после разблокировки.
- Шаблоны push — закрытый перечень в коде. Тест проверяет, что у шаблона
  нет текстовых параметров.
- Токены устройств хранятся в ячейке (`iam`), удаляются при выходе и при
  отзыве устройства.

Отправка push идёт через outbox ([0020](0020-transactional-outbox.md)).

### 7. PHI на устройстве

Врачи работают с медданными на личных телефонах и планшетах.
Обязательные требования для обоих приложений в оболочке:

- блокировка приложения PIN или биометрией, автоблокировка при
  бездействии (для приложения клиники — обязательно);
- Android: `FLAG_SECURE` на экранах с PHI (без скриншотов и записи
  экрана); iOS: содержимое скрывается в переключателе приложений;
- PHI не кэшируется на устройстве в открытом виде. Если кэш нужен —
  зашифрованный, с TTL, очищается при выходе;
- PHI не попадает в логи устройства и отчёты о сбоях. Сервис отчётов о
  сбоях — внешний API, и для него отдельно решается: в регионе или без
  данных пользователя;
- администратор клиники может удалённо отозвать сессии сотрудника
  (0017).

## Альтернативы

- **Одно приложение с переключателем «пациент / персонал».** Одна
  страница в сторе, но оба профиля безопасности в одном приложении: TOTP,
  короткие сессии и ограничения экранов персонала мешают пациенту. Режим
  приложения становится состоянием клиента, а не аудиторией сессии.
- **Нативные приложения (Swift, Kotlin) или Flutter / React Native.**
  Лучше UX и производительность, но вторая и третья кодовая база и
  другие навыки команды. Пересматривается, если WebView станет
  ограничением.
- **Только PWA без сторов.** Почти бесплатно, но на iOS ограничены push и
  фоновая работа, нет присутствия в App Store, и пациенты меньше доверяют
  «сайту на экране».
- **Один веб-хост для обоих приложений** (`app.<домен>/clinic`,
  `app.<домен>/me`). Один origin — одна граница безопасности браузера:
  XSS в пациентской части работает в том же origin, что и клиника.
  Привязка cookie к origin (0017) становится невозможной.

## Последствия

- Переход с `app.<домен>` на `clinic.` и `my.` — в конфиге origin (0018) и
  DNS.
- Требования сторов, которые влияют на IAM:
  - удаление аккаунта внутри приложения (Apple требует его при наличии
    регистрации). Медкарты клиник при этом хранятся по закону, удаляется
    аккаунт и профиль. Детали — ADR IAM;
  - политика конфиденциальности и декларации данных (App Privacy, Data
    safety).
- Не код, но на критическом пути: аккаунты разработчика Apple и Google на
  компанию. Для Apple нужен D-U-N-S номер, оформление занимает недели.
- Порядок работ: веб клиники первым. Оболочки обоих приложений со входом
  собираются уже в 1.7, чтобы рано проверить bearer, мобильную
  CORS-политику и сборку в CI.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.310(c), (d) (рабочие станции и носители),
    §164.312(a)(2)(iii);
  - ISO/IEC 27001:2022 A.8.1 (пользовательские конечные устройства),
    A.6.7 (удалённая работа), A.5.14 (передача информации);
  - ISO/IEC 27701 (обработка PII третьими сторонами — FCM, APNs);
  - SOC 2 CC6.7.
