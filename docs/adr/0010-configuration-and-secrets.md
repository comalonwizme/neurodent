# 0010. Конфигурация и секреты

- Статус: Принято
- Дата: 2026-09-27

## Контекст

Процесс конфигурируется окружением (12-factor, одна конфигурация на
ячейку — см. [0003](0003-cells-and-data-residency.md)). Ошибка конфигурации
в медицинской системе опасна по-разному: опечатка `WRITE_TIMEOUT=10h`
молча выключает защиту, debug-логи в проде пишут PHI, DSN в логе — это
пароль к базе медкарт.

## Решение

- **Переменные с префиксом `NEURODENT_`**, у каждого дефолта — комментарий
  «почему столько».
- **Двухэтапная валидация** (`internal/config`): сначала каждое поле
  (парсинг, диапазон; пустая строка — ошибка, а не дефолт), затем
  кросс-полевые инварианты — только для валидных полей, чтобы одна опечатка
  давала одну ошибку. Все ошибки возвращаются сразу.
- **Инварианты, завязанные на безопасность:** debug-логи запрещены в prod;
  `HANDLER_TIMEOUT < WRITE_TIMEOUT`; `DB_STATEMENT_TIMEOUT < HANDLER_TIMEOUT`;
  `SHUTDOWN + DRAIN ≤` бюджета остановки оркестратора.
- **Секреты — тип `config.Secret`**: fmt (любой глагол, через
  `fmt.Formatter`), slog и JSON видят `[REDACTED]`, значение достаётся
  только вызовом `Reveal()`. DSN не входит в `LogValue` (allowlist).
  Ошибки разбора секретов не оборачивают текст драйвера.
- **TLS до БД обязателен вне dev** (см. [0007](0007-postgres-driver-pgx.md)).
- **Dev-пароли не в репозитории**: `make db-env` генерирует `.env`
  (в .gitignore) со случайными паролями.

## Альтернативы

- **Файл конфигурации (YAML).** Ещё один артефакт на ячейку и соблазн
  положить секреты рядом с кодом; оркестраторы и менеджеры секретов
  отдают значения через окружение.
- **Секреты строкой.** Одна случайная `%v` или `slog.Any("cfg", cfg)` — и
  пароль в логах. Тест `TestSecret_NeverPrinted` поймал такую утечку
  (`%d` печатает поля структуры в обход `String()`), поэтому `Format`
  обязателен.

## Последствия

- Процесс не стартует с невалидным конфигом и называет все ошибочные
  переменные сразу.
- Место, где секрет покидает `Secret`, ищется `grep Reveal`.
- Добавление поля в лог конфига требует правки теста allowlist — это
  намеренное трение.
- Спроектировано по контролям: ISO/IEC 27001:2022 A.8.9 (управление
  конфигурацией), A.5.17 (аутентификационная информация), A.8.15
  (журналирование); HIPAA 45 CFR §164.312(e)(1); SOC 2 CC6.1.
