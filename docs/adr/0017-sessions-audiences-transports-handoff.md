# 0017. Сессии: аудитории, два транспорта, переход между приложениями

- Статус: Принято (после ревью, 2026-09-28)
- Дата: 2026-09-28
- Заменяет: [0005](0005-server-side-sessions.md)
- Связанные: 0011 (субъект транзакции), 0014 (аудит), 0016 (rate limit), 0018 (CORS и CSRF), 0019 (клиентские приложения)

## Контекст

[0005](0005-server-side-sessions.md) описывает одну сессию для одного
клиента: браузер, cookie `SameSite=Lax`. Решения
[0019](0019-client-applications-and-platforms.md) меняют картину:

- **Два приложения на один аккаунт.** NeuroDent для пациента и NeuroDent
  Clinic для персонала. У них разный профиль безопасности: персоналу
  нужен второй фактор и короткие сессии, пациенту — нет.
- **Каждое приложение есть в вебе и в мобильной оболочке** (Capacitor).

Из этого следуют три проблемы, которые 0005 не решает.

1. **Cookie не работают в мобильной оболочке.** Страница в WebView
   Capacitor имеет origin `capacitor://localhost` (iOS) или
   `https://localhost` (Android). Для `api.<домен>` это другой site:
   `SameSite`-cookie не отправляются, а WKWebView на iOS дополнительно
   блокирует сторонние cookie.
2. **Оба веб-приложения ходят на один хост `api.<домен>`.** В браузере
   у этого хоста одна банка cookie. Если человек вошёл и в `clinic.`, и
   в `my.`, запрос с любого из двух сайтов понесёт cookie обоих. XSS на
   пациентском сайте смог бы вызвать API клиники с cookie сотрудника.
3. **Переход между приложениями.** Основатель клиники — тоже пациент.
   Он должен переходить из одного приложения в другое без повторного
   ввода телефона и пароля, но не в обход второго фактора персонала.

## Решение

### 1. Что остаётся из 0005

- Сессия хранится на сервере. Клиент получает непрозрачный токен из
  CSPRNG, **256 бит**.
- На сервере хранится SHA-256 токена. HMAC не нужен: у токена полная
  энтропия, перебор невозможен (в отличие от телефонов в 0016).
- Отзыв — удаление записи. Срок жизни — скользящий idle-таймаут плюс
  абсолютный максимум.

### 2. Аудитория сессии

У каждой сессии есть **аудитория**: `clinic` или `patient`. Она задаётся
при выдаче и не меняется.

API разделён на группы маршрутов, и каждая принимает только свою
аудиторию:

| Группа | Аудитория | Какой scope может построить (0011) |
|---|---|---|
| `/v1/auth/…` | любая или никакой: выдача, продление, отзыв | `anonymous`, `user` |
| `/v1/clinic/…` | `clinic` | `user` вне клиники; `staff` в клинике после проверки членства |
| `/v1/me/…` | `patient` | `user`, `patient_resolve`, `patient` |

- Сессия чужой аудитории — **401**, как отсутствие сессии. Сессия
  пациента не даёт `staff` ни при каких условиях, сессия клиники не даёт
  `patient` и `patient_resolve`.
- Правило «аудитория → допустимые виды субъекта» проверяет построитель
  scope в IAM. Это первый рубеж перед RLS.
- Один аккаунт, две независимые сессии. Выход из одного приложения не
  завершает другое. «Выйти везде» отзывает обе аудитории.

### 3. Два транспорта

У каждой сессии есть **транспорт**: `cookie` (веб) или `bearer`
(мобильная оболочка). Он тоже задаётся при выдаче и не меняется.

**Cookie** — для веба.
- Имя по аудитории: `__Host-nd_clinic` и `__Host-nd_patient`.
- Атрибуты: `HttpOnly; Secure; Path=/; SameSite=Strict`, без `Domain`.
- `Strict`, а не `Lax`, как было в 0005: `clinic.` и `my.` — same-site с
  `api.`, поэтому `fetch` к API несёт cookie и при `Strict`. Переходы
  верхнего уровня с чужих сайтов cookie не несут: для API они не нужны.
- Группа маршрутов выбирает имя cookie. `/v1/clinic/…` читает только
  `__Host-nd_clinic`, `/v1/me/…` — только `__Host-nd_patient`.

**Bearer** — для мобильной оболочки.
- Заголовок `Authorization: Bearer <токен>`.
- На устройстве токен хранится **только** в Keychain (iOS) или Keystore
  (Android) через плагин защищённого хранилища. `localStorage`,
  `Preferences` и файлы не используются.

**Правила для обоих транспортов:**
- Токен cookie-сессии, предъявленный как bearer, — 401, и наоборот.
  Украденное значение cookie нельзя использовать из мобильного клиента
  или curl.
- Запрос, в котором есть и cookie сессии, и `Authorization`, — 401. Какой
  из двух принадлежит клиенту, неизвестно, и угадывать сервер не должен.
- Веб-клиент не может прислать `Authorization`: preflight с веб-origin его
  не разрешает (0018). Поэтому bearer-токен никогда не окажется в
  JS-доступном хранилище браузера, где его украдёт XSS.

### 4. Cookie-сессия привязана к origin своей аудитории

Для cookie-транспорта `Origin` запроса должен входить в список
веб-origin **этой аудитории**: `NEURODENT_CLINIC_WEB_ORIGINS` или
`NEURODENT_PATIENT_WEB_ORIGINS` (0018). Иначе — 401, как без сессии.

- Запросы `clinic.` → `api.` и `my.` → `api.` cross-origin, поэтому браузер
  ставит `Origin` на все запросы `fetch`, включая `GET`.
- Если `Origin` нет у запроса с cookie, это не наш веб-клиент — 401.

Именно это закрывает проблему 2. XSS на `my.` отправит `__Host-nd_clinic`
на `/v1/clinic/…`, но `Origin: https://my.<домен>` не входит в список
origin клиники.

### 5. Уровень аутентификации

Сессия хранит:
- `authenticated_at` — когда подтверждён первичный вход;
- `mfa_at` — когда подтверждён второй фактор, может быть пустым.

Правила:
- Группа `/v1/clinic/…` требует `mfa_at`. Сессия клиники без второго
  фактора допускает только эндпоинты завершения входа (ввод TOTP,
  подключение TOTP при первом входе).
- **Повторное подтверждение** для чувствительных действий — свежий
  `mfa_at` (для персонала) или `authenticated_at` (для пациента) в
  пределах окна. Примеры действий: смена номера и пароля, управление
  сотрудниками, экспорт данных.
- Какие факторы бывают и как их проверять (пароль, TOTP, позже passkey),
  решает ADR IAM. Этот ADR фиксирует только, что сессия хранит уровень.

### 6. Время жизни по аудитории и транспорту

Значения по умолчанию, настраиваются конфигом. Окончательные цифры — в
ТЗ IAM.

| Аудитория, транспорт | Idle | Абсолютный максимум |
|---|---|---|
| `clinic`, `cookie` | 30 мин | 12 ч |
| `clinic`, `bearer` | 30 мин | 12 ч |
| `patient`, `cookie` | 24 ч | 30 дней |
| `patient`, `bearer` | 30 дней | 90 дней |

Привязка устройства (ключ в Keychain/Keystore, разблокировка по PIN или
биометрии) продлевает мобильный вход без SMS и пароля. Это отдельное
решение ADR IAM вместе с кабинетом пациента, модель сессии для него не
меняется.

### 7. Переход между приложениями (handoff)

Переход передаёт вход из одного приложения в другое через сервер.
Сессия одного приложения никогда не используется другим.

1. Приложение-источник: `POST /v1/auth/handoff` с целевой аудиторией.
   Нужна активная сессия.
2. Сервер создаёт одноразовый код:
   - 256 бит из CSPRNG, TTL 60 секунд;
   - хранится SHA-256;
   - привязан к пользователю, сессии-источнику и целевой аудитории.
3. Код передаётся в **фрагменте URL** (`#code=…`), а не в query:
   фрагмент не уходит на сервер статики, в логи прокси и в `Referer`.
   - Веб: переход верхнего уровня на `https://clinic.<домен>/auth/handoff#code=…`
     (или `my.`).
   - Мобильные: только проверенные по домену Universal Links (iOS) и App
     Links (Android) на тот же путь. Свои URL-схемы (`neurodent://`)
     запрещены: на Android их может перехватить чужое приложение.
4. Целевое приложение: `POST /v1/auth/handoff/exchange` с кодом и своим
   транспортом. Обмен атомарный (`DELETE … RETURNING`): второе
   предъявление того же кода — отказ.
5. Новая сессия создаётся в целевой аудитории с `authenticated_at` =
   сейчас и **`mfa_at` = пусто**.

Handoff заменяет только телефон и пароль, **второй фактор персонала он не
заменяет никогда**. Перехваченный код даёт сессию клиники, которая без
TOTP не видит ни одного эндпоинта с данными.

Дополнительно:
- Лимит выпуска кодов по пользователю — политика `iam.handoff.user` (0016).
- События аудита: `iam.handoff.issued`, `iam.handoff.exchanged`, отказ
  при обмене — `outcome = denied`.
- Сессия-источник не меняется.

### 8. Тип клиента в журнале аудита

В `audit.events` добавляется поле `client`:

- закрытый перечень `clinic-web`, `clinic-mobile`, `patient-web`,
  `patient-mobile`, CHECK в БД;
- значение выводится из сессии (аудитория + транспорт) и кладётся в
  контекст запроса middleware аутентификации;
- `Recorder` берёт его из контекста, как `request_id`, вызывающий его не
  передаёт;
- NULL — событие без сессии (`anonymous`, `system`).

Значение из заголовков или тела запроса не берётся никогда. Иначе клиент
сам назвал бы себя другим приложением.

## Альтернативы

- **Одна сессия на оба приложения** (одна cookie на родительский домен,
  общий токен). Проще переход между приложениями, но смешиваются
  аудитории: сессия пациента оказывается сессией персонала, а cookie на
  `.<домен>` видят все поддомены, включая лендинг.
- **Cookie в мобильной оболочке через нативный HTTP-слой**
  (`CapacitorHttp`, cookie в нативном хранилище). Одна модель
  транспорта, но это хрупко (поведение различается между iOS и Android и
  между версиями), а защита от CSRF для такого «браузера без браузера»
  становится неочевидной.
- **JWT для мобильных.** Отклонено в 0005: отзыв требует того же
  серверного состояния, плюс управление ключами подписи.
- **Общая группа Keychain двух приложений для единого входа.** Apple
  разрешает её приложениям одной команды, но это снова одна сессия на
  две аудитории. Допустимо хранить там только идентификатор устройства.
- **Handoff-код в query-параметре.** Попадает в логи сервера статики,
  прокси и в `Referer`.
- **Handoff, пропускающий второй фактор, если он недавно подтверждён в
  источнике.** Удобнее для основателя, но из пациентского приложения
  второго фактора нет, а переход из приложения клиники в пациентское
  второй фактор и так не требует.
- **Разные поддомены API на аудиторию** (`api-clinic.`, `api-my.`). Банки
  cookie разделил бы браузер, но появляются два origin API, два
  сертификата и дублирование CORS. Привязка cookie к origin (п. 4)
  решает ту же задачу в одном месте.

## Последствия

- Таблица `iam.sessions` (`cell-global`, 0011): аудитория, транспорт,
  хеш токена, `authenticated_at`, `mfa_at`, `last_seen_at`, `expires_at`.
  Таблица одноразовых handoff-кодов. Точная схема — в ТЗ IAM.
- В `openapi.yaml` три схемы безопасности: `clinicCookie` и
  `patientCookie` (apiKey в cookie), `bearerAuth` (http bearer). Группа
  маршрутов объявляет свои схемы.
- 401 по RFC 9110 требует `WWW-Authenticate`. Для bearer —
  `Bearer realm="neurodent"`. Для cookie стандартной схемы нет: вариант
  выбирается в ТЗ IAM (открытый вопрос из 0005 остаётся открытым).
- Миграция: столбец `audit.events.client` с CHECK. ADR-0014 в остальном не
  меняется.
- Тесты:
  - сессия чужой аудитории — 401;
  - cookie чужой аудитории с `Origin` другого приложения — 401;
  - cookie-токен, предъявленный как bearer, — 401, и наоборот;
  - cookie и `Authorization` в одном запросе — 401;
  - сессия клиники без `mfa_at` видит только эндпоинты завершения входа;
  - handoff: повторный обмен — отказ; истёкший код — отказ; код другой
    аудитории — отказ; новая сессия клиники без `mfa_at`.
- Мутации, которые обязаны ронять тесты:
  - убрана проверка аудитории;
  - убрана проверка `Origin` для cookie;
  - handoff выставляет `mfa_at`.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(d) (аутентификация), §164.312(a)(2)(iii)
    (автоматическое завершение сеанса);
  - ISO/IEC 27001:2022 A.8.5 (безопасная аутентификация), A.5.15
    (управление доступом);
  - SOC 2 CC6.1, CC6.2.
