# 0011. Идентичность, клиники, ячейки, классы таблиц

- Статус: Предложено
- Дата: 2026-09-27
- Связанные: 0003 (ячейки), 0004 (RLS), 0012 (scope транзакции), 0014 (аудит)

## Контекст

Каждый человек сначала регистрируется как пациент. Роли (врач, основатель
клиники, администратор) он получает внутри приложения после верификации.
Клиника добавляет сотрудников только из уже зарегистрированных
пользователей. Пациент видит свою историю во всех клиниках.

Tenant = клиника ([0004](0004-medical-record-ownership-and-rls.md)),
ячейка = регион ([0003](0003-cells-and-data-residency.md)). RLS по
`app.tenant_id` отделяет клиники друг от друга. Но внутри одной клиники
пациенты не отделены: забытая проверка в эндпоинте кабинета пациента
(`GET /me/visits/{id}` без сверки владельца, классический IDOR) отдаст
чужую медзапись, и RLS этому не помешает.

Первый бизнес-модуль (IAM) не должен принимать эти решения неявно: где
живёт аккаунт, кто владеет клиникой как сущностью, какие таблицы
изолируются и как.

## Решение

### 1. Аккаунт живёт в домашней ячейке

Ячейка выбирается при регистрации; сейчас она одна — KZ. Данные аккаунта
(телефон, ФИО, ИИН) — персональные данные, и на них распространяются
требования резидентности той же ячейки.

Федерация аккаунтов между ячейками — не в этой фазе. Модель её не
запрещает: идентификаторы — UUID, без последовательностей, уникальных
только в одной БД.

Следствие для этой фазы: **сотрудник клиники — пользователь той же
ячейки, что и клиника.** Членство хранится в `iam` ячейки, чужих аккаунтов
она не видит.

### 2. Разделение модулей

- `iam` — доступ:
  - пользователи и учётные данные, сессии;
  - платформенные роли и их верификация;
  - **членство пользователя в клинике и роли внутри неё**. Это вопрос
    «кто что может», поэтому он в IAM, а не в `org`.
- `org` — клиника как сущность: профиль, адрес, часовой пояс (IANA),
  валюта, настройки. `tenant_id` = `org.clinics.id`.

Связь `iam.memberships.clinic_id → org.clinics.id` — **без внешнего ключа
между схемами** (правило модулей — в
[0012](0012-module-template-and-cross-module-transactions.md)).

Целостность обеспечивает оркестрация: клинику и членство основателя
создаёт один use case `org` в одной транзакции, вызывая контракт `iam`.
Направление зависимости — **`org` → `iam`**, обратной нет. Граф модулей
ацикличен (0012). Добавить сотрудника может только участник клиники с
правом управления, поэтому `iam` не нужно спрашивать `org`, существует
ли клиника: членство администратора — уже доказательство.

### 3. Классы таблиц

Класс указывается первой строкой `COMMENT ON TABLE` в машиночитаемом виде
`class=<класс>; <описание>`. Класс — не просто документация: его
проверяет тест схемы (см. «Последствия»).

| Класс | Примеры | Изоляция |
|---|---|---|
| `tenant` | склад, прайс, настройки расписания | RLS по `app.tenant_id` (ENABLE + FORCE), как `platform.rls_probe` |
| `patient-owned` | медзапись, визиты, планы лечения | `tenant` **плюс** RESTRICTIVE-политика по субъекту (п. 4) |
| `cell-global` | `iam.users`, `iam.sessions`, `org.clinics` | без tenant-RLS; доступ только через код модуля-владельца |

Служебные таблицы платформы описываются своими ADR: журнал аудита — класс
`audit` ([0014](0014-audit-log.md)); счётчики rate limit — `cell-global`
([0016](0016-rate-limiting-and-trusted-proxies.md)).

**Правило классификации:** таблица клиники, в которой есть `patient_id`,
обязана быть `patient-owned`. Исключение — только с обоснованием в
миграции.

### 4. Субъект транзакции, fail-closed

Кроме `app.tenant_id`, транзакция выставляет:

- `app.actor_kind` — вид субъекта: `staff`, `patient` или `system`
  (в global-транзакциях вне клиники — `user`, `anonymous` или `system`,
  см. 0012);
- `app.actor_id` — пользователь, от имени которого идёт транзакция; для
  `system` и `anonymous` не выставляется;
- `app.patient_id` — только для `actor_kind = patient`.

Значения ставит `WithinTx` из явного scope ([0012](0012-module-template-and-cross-module-transactions.md))
через `SET LOCAL`.

RESTRICTIVE-политика `patient-owned` таблиц:

```sql
CREATE POLICY subject_access ON <table> AS RESTRICTIVE
    USING (
        (SELECT platform.current_actor_kind()) IN ('staff', 'system')
        OR ((SELECT platform.current_actor_kind()) = 'patient'
            AND patient_id = (SELECT platform.current_patient_id()))
    )
    WITH CHECK (<то же выражение>);
```

Как это работает:

- `actor_kind` не выставлен или содержит неизвестное значение — ноль строк;
- пациент без `patient_id` — ноль строк;
- пациент может записать строку только про себя (`WITH CHECK`).

Доступ сотрудника по ролям внутри клиники (врач видит своих пациентов,
регистратор — только расписание) — первый рубеж, он в коде IAM. RLS не
дублирует матрицу ролей: это второй рубеж против класса ошибок «пациент
видит чужое».

**Функции-аксессоры** `platform.current_tenant_id()`,
`platform.current_actor_kind()`, `platform.current_actor_id()`,
`platform.current_patient_id()` — `STABLE`, внутри `NULLIF(…, '')`:

- ловушка «пустая строка вместо NULL» (см. `0001`) закрыта в одном месте,
  а не в каждой политике;
- обёртка `(SELECT …)` в политике вычисляется один раз на запрос
  (InitPlan), а не на каждую строку.

### 5. `patient_id` — это пациент клиники, а не аккаунт

**Уточнение умолчания.** В `patient-owned` таблицах `patient_id` —
идентификатор пациента **этой клиники** (карточка пациента, tenant-таблица
будущего модуля пациентов/EMR), а не `iam.users.id`.

Карточка ссылается на аккаунт полем `user_id`, которое может быть пустым.

Почему не `user_id` напрямую:

- у клиники будут пациенты без аккаунта: дети, импорт базы из прежней
  системы, запись по телефону через регистратуру;
- опекун (родитель) действует от имени пациента-ребёнка.

Как `app.patient_id` попадает в транзакцию. Код кабинета пациента:

1. в отдельном шаге (`actor_kind = system`, scope клиники) находит карточку
   по `user_id` или по связи опекунства;
2. проверяет право (первый рубеж);
3. открывает транзакцию с `actor_kind = patient` и `patient_id` найденной
   карточки.

Одна транзакция — один субъект. Опекун, переключившийся на профиль
ребёнка, работает с `patient_id` ребёнка.

### 6. Записи в нескольких клиниках

Кабинет пациента читает их по одной клинике за транзакцию, каждый раз с
`actor_kind = patient` и карточкой этой клиники. Это уже зафиксировано в
[0004](0004-medical-record-ownership-and-rls.md).

### Отличия от решения по умолчанию из ТЗ 0.7

- Добавлен `app.actor_id`. Он нужен журналу аудита, чтобы `WITH CHECK`
  не дал записать событие от чужого имени ([0014](0014-audit-log.md)).
- `patient_id` определён как пациент клиники, а не аккаунт (п. 5).
- Формат класса в комментарии (`class=…;`) и функции-аксессоры для политик.
- Явный запрет FK между схемами разных модулей.

## Альтернативы

- **Без RESTRICTIVE-политики, изоляция пациентов только в коде.** Проще,
  но IDOR в кабинете пациента — одна из самых частых уязвимостей
  медицинских порталов, а цена ошибки — медзапись чужого человека.
- **`patient_id` = `iam.users.id`.** Нет таблицы-карточки и шага
  разрешения. Но исключены пациенты без аккаунта и опекунство, а
  медзапись клиники оказывается привязана к платформенному аккаунту, хотя
  принадлежит клинике.
- **`app.patient_ids` — массив субъектов** (сам пациент и все
  подопечные) в одной транзакции. Удобно для «семейного» экрана, но
  расширяет видимость одной транзакции. Предпочтено «одна транзакция —
  один субъект».
- **Запрет пациентам на обычные `tenant`-таблицы** (политика `tenant`
  требует `actor_kind IN ('staff','system')`). Строже: неверно
  классифицированная таблица с данными пациентов не утечёт пациенту. Но
  публичные данные клиники (услуги, врачи, свободные слоты) придётся
  читать через `system` или вводить класс `tenant-public`. Оставлено как
  вариант, если тест схемы окажется недостаточным.
- **Отдельная роль БД на модуль** (`iam_rw`, `org_rw`, …, переключение
  `SET LOCAL ROLE` на входе в модуль). Это второй рубеж для `cell-global`
  таблиц: модуль физически не может читать чужую схему. Стоит сложности в
  межмодульных транзакциях (смена роли внутри транзакции при вызове
  контракта). Кандидат на усиление, когда появятся `cell-global` таблицы
  с чувствительными данными, кроме `iam`.
- **FK между схемами модулей.** Целостность «бесплатно», но модуль
  перестаёт владеть схемой: миграции модулей связаны, а вынос модуля
  требует разрыва ключей.

## Последствия

- У `cell-global` таблиц нет второго рубежа в БД: `iam.users` защищает
  только код `iam` и правило «доступ через контракт» (проверяется тестом
  архитектуры, [0012](0012-module-template-and-cross-module-transactions.md)).
  Это сознательный риск. Вариант усиления — роли БД на модуль (см.
  «Альтернативы»).
- **Тест схемы** (integration, по `pg_catalog`):
  - у каждой таблицы вне `public` есть `class=`;
  - у `tenant` и `patient-owned`: ENABLE + FORCE RLS и tenant-политика;
  - у `patient-owned` есть RESTRICTIVE-политика `subject_access`;
  - у таблиц клиники со столбцом `patient_id` класс `patient-owned`.

  Новая таблица без RLS не пройдёт CI.
- `WithinTx` выставляет до четырёх параметров на транзакцию. Цена —
  микросекунды.
- Кабинету пациента нужен шаг разрешения «аккаунт → карточка в клинике»
  под `actor_kind = system`. Это узкое место для ревью: `system`-транзакция
  видит всех пациентов клиники.
- Часовой пояс клиники — IANA-имя. Бинарник встраивает базу часовых поясов
  (`import _ "time/tzdata"`), чтобы не зависеть от образа контейнера.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(a)(1), §164.308(a)(4);
  - GDPR ст. 25, 32;
  - ISO/IEC 27001:2022 A.5.15, A.8.3;
  - SOC 2 CC6.1, CC6.3.

## Открытые вопросы (решаются в ТЗ IAM)

- Способ входа: телефон + OTP или email + пароль.
- Собирается ли ИИН при регистрации; хранение и маскирование ИИН.
- Процесс верификации врача (лицензия) и основателя клиники.
- 2FA для персонала.
- Может ли клиника завести пациента без аккаунта и как он потом
  «забирает» карточку (п. 5 это допускает).
- Опекунство: кто и как подтверждает связь родитель ↔ ребёнок.
- Доступ поддержки NeuroDent к данным клиники (break-glass): только по
  разрешению клиники, ограниченный по времени, с аудитом. Отдельный ADR.
