# 0011. Идентичность, клиники, ячейки, классы таблиц

- Статус: Принято (после ревью, 2026-09-27)
- Дата: 2026-09-27
- Связанные: 0003 (ячейки), 0004 (RLS), 0012 (scope транзакции), 0014 (аудит)

## Контекст

Каждый человек сначала регистрируется как пациент. Роли (врач, основатель
клиники, администратор) он получает внутри приложения после верификации.
Клиника добавляет сотрудников только из уже зарегистрированных
пользователей. Пациент видит свою историю во всех клиниках.

Tenant = клиника ([0004](0004-medical-record-ownership-and-rls.md)),
ячейка = регион ([0003](0003-cells-and-data-residency.md)). RLS по
`app.tenant_id` отделяет клиники друг от друга. Но внутри одной клиники
пациенты не отделены: забытая проверка в эндпоинте кабинета пациента
(`GET /me/visits/{id}` без сверки владельца, классический IDOR) отдаст
чужую медзапись, и RLS этому не помешает.

Первый бизнес-модуль (IAM) не должен принимать эти решения неявно: где
живёт аккаунт, кто владеет клиникой как сущностью, какие таблицы
изолируются и как.

## Решение

### 1. Аккаунт живёт в домашней ячейке; одна ячейка на пользователя

Ячейка выбирается при регистрации; сейчас она одна — KZ. Данные аккаунта
(телефон, ФИО, ИИН) — персональные данные, и на них распространяются
требования резидентности той же ячейки.

**Ограничение этой фазы: пользователь существует ровно в одной ячейке.**
Он может быть сотрудником и пациентом только клиник своей ячейки.
Клиника другой ячейки его не видит и не может добавить ни сотрудником,
ни пациентом с доступом к кабинету.

Федерация аккаунтов между ячейками — не в этой фазе. Модель её не
запрещает: идентификаторы — UUID, без последовательностей, уникальных
только в одной БД. Снятие ограничения — отдельный ADR.

### 2. Разделение модулей

- `iam` — доступ:
  - пользователи и учётные данные, сессии;
  - платформенные роли и их верификация;
  - **членство пользователя в клинике и роли внутри неё**. Это вопрос
    «кто что может», поэтому он в IAM, а не в `org`.
- `org` — клиника как сущность: профиль, адрес, часовой пояс (IANA),
  валюта, настройки. `tenant_id` = `org.clinics.id`.

Связь `iam.memberships.clinic_id → org.clinics.id` — **без внешнего ключа
между схемами** (правило модулей — в
[0012](0012-module-template-and-cross-module-transactions.md)).

Целостность обеспечивает оркестрация: клинику и членство основателя
создаёт один use case `org` в одной транзакции, вызывая контракт `iam`.
Направление зависимости — **`org` → `iam`**, обратной нет. Граф модулей
ацикличен (0012). Добавить сотрудника может только участник клиники с
правом управления, поэтому `iam` не нужно спрашивать `org`, существует
ли клиника: членство администратора — уже доказательство.

### 3. Субъект транзакции

Кроме `app.tenant_id`, транзакция выставляет:

- `app.actor_kind` — вид субъекта:
  - в транзакции клиники — `staff`, `patient`, `patient_resolve` или
    `system`;
  - вне клиники — `user`, `anonymous` или `system`;
- `app.actor_id` — пользователь, от имени которого идёт транзакция; для
  `system` и `anonymous` не выставляется;
- `app.patient_id` — только для `actor_kind = patient`.

Значения ставит `WithinTx` из явного scope ([0012](0012-module-template-and-cross-module-transactions.md))
через `SET LOCAL`.

**Функции-аксессоры** `platform.current_tenant_id()`,
`platform.current_actor_kind()`, `platform.current_actor_id()`,
`platform.current_patient_id()` — `STABLE`, внутри `NULLIF(…, '')`:

- ловушка «пустая строка вместо NULL» (см. `0001`) закрыта в одном месте;
- в политиках вызов оборачивается в `(SELECT …)` — он вычисляется один раз
  на запрос (InitPlan), а не на каждую строку.

Не выставлено или неизвестно — политики дают ноль строк. Это fail-closed.

### 4. Классы таблиц и шаблоны политик

Класс указывается первой строкой `COMMENT ON TABLE` в машиночитаемом виде
`class=<класс>; <описание>`.

**Принцип:**

- **RESTRICTIVE-политики кодируют инварианты изоляции**: «только своя
  клиника», «пациент — только своё». Все RESTRICTIVE-политики должны
  выполняться одновременно, и новая политика их не ослабит.
- **PERMISSIVE-политики говорят, кому и что разрешено.**

Имена политик фиксированы. Тест схемы сверяет **точный набор** политик
каждого класса: лишняя permissive-политика — ошибка CI.

| Класс | Что в нём | RESTRICTIVE | PERMISSIVE |
|---|---|---|---|
| `tenant` | данные клиники, не предназначенные пациенту: склад, финансы, настройки | `tenant_guard` | `staff_access` |
| `tenant-public` | данные клиники, которые видит пациент: услуги и цены, врачи, свободные слоты | `tenant_guard` | `staff_access`, `patient_read` (только SELECT) |
| `patient-owned` | данные о конкретном пациенте: медзапись, визиты, планы лечения | `tenant_guard`, `subject_guard` | `staff_access`, `patient_access` |
| `patient-registry` | карточки пациентов клиники и связи опекунства | `tenant_guard`, `subject_guard` | `staff_access`, `patient_read` (только SELECT) |
| `cell-global` | `iam.users`, `iam.sessions`, `org.clinics` | — (без RLS) | — |

Выражения политик:

```sql
-- все классы клиники
tenant_guard   AS RESTRICTIVE  USING (tenant_id = (SELECT platform.current_tenant_id()))
staff_access                   USING ((SELECT platform.current_actor_kind()) IN ('staff', 'system'))

-- tenant-public
patient_read   FOR SELECT      USING ((SELECT platform.current_actor_kind()) = 'patient')

-- patient-registry: шагу разрешения (п. 5) нужны только карточки
patient_read   FOR SELECT      USING ((SELECT platform.current_actor_kind()) IN ('patient', 'patient_resolve'))

-- patient-owned
patient_access                 USING ((SELECT platform.current_actor_kind()) = 'patient')
subject_guard  AS RESTRICTIVE  USING (
    (SELECT platform.current_actor_kind()) IN ('staff', 'system')
    OR ((SELECT platform.current_actor_kind()) = 'patient'
        AND patient_id = (SELECT platform.current_patient_id())))

-- patient-registry (таблица карточек; у таблицы опекунства — своё поле субъекта)
subject_guard  AS RESTRICTIVE  USING (
    (SELECT platform.current_actor_kind()) IN ('staff', 'system')
    OR ((SELECT platform.current_actor_kind()) = 'patient'
        AND id = (SELECT platform.current_patient_id()))
    OR ((SELECT platform.current_actor_kind()) = 'patient_resolve'
        AND (user_id = (SELECT platform.current_actor_id())
             OR id IN (SELECT ward_patient_id FROM <опекунство>
                       WHERE guardian_user_id = (SELECT platform.current_actor_id())))))
```

`WITH CHECK` у каждой политики совпадает с `USING`.

Что это даёт:

- **`tenant`-таблицы пациенту недоступны вовсе.** Таблица с данными
  пациентов, по ошибке оставленная в классе `tenant`, не утечёт в
  кабинет.
- **`tenant-public` пациент только читает.**
- **В `patient-owned` пациент видит и меняет только строки своей
  карточки.**
- **`patient_resolve` видит только свои карточки и карточки
  подопечных** — и больше ничего во всей БД.

**Правила классификации** (проверяет тест схемы):

- у каждой таблицы вне `public` есть `class=`;
- набор политик совпадает с шаблоном класса;
- у классов клиники ENABLE + FORCE RLS;
- таблица клиники со столбцом `patient_id` не может быть `tenant` или
  `tenant-public`.

Служебные таблицы платформы описываются своими ADR: журнал аудита — класс
`audit` ([0014](0014-audit-log.md)); счётчики rate limit — `cell-global`
([0016](0016-rate-limiting-and-trusted-proxies.md)).

### 5. Путь пациента: без `system`

`patient_id` в медданных — идентификатор пациента **этой клиники**
(карточки в `patient-registry`), а не `iam.users.id`. Карточка ссылается
на аккаунт полем `user_id`, которое может быть пустым: у клиники будут
пациенты без аккаунта (дети, импорт базы, запись через регистратуру).
Опекун действует от имени подопечного.

Кабинет пациента работает в два шага, и **ни один из них не использует
`system`**:

1. **Разрешение:** `scope.Tenant(clinicID, scope.PatientResolve(userID))`.
   RLS отдаёт только карточки, где `user_id` = этот пользователь, и
   карточки его подопечных по таблице опекунства. Код выбирает карточку
   (свою или подопечного — это первый рубеж: проверка права).
2. **Работа:** `scope.Tenant(clinicID, scope.Patient(userID, patientID))`
   с выбранной карточкой. Одна транзакция — один субъект.

Даже ошибка в коде шага 1 не покажет чужую карточку: выборку ограничивает
RESTRICTIVE-политика.

Остаточный риск: на шаге 2 БД доверяет `patientID`, который передал код.
Связь «пользователь ↔ карточка» проверяется на шаге 1 под RLS, но не
перепроверяется на шаге 2. Усиление — проверка связи внутри
`subject_guard` — откладывается до ADR модуля пациентов: там появятся
реальные таблицы карточек и опекунства.

Конкретные таблицы карточек и опекунства принадлежат будущему модулю
пациентов. В 0.7 шаблон класса `patient-registry` и путь разрешения
доказываются технической probe-таблицей.

### 6. Записи в нескольких клиниках

Кабинет пациента читает их по одной клинике за транзакцию, каждый раз
проходя шаги п. 5 в этой клинике. Это уже зафиксировано в
[0004](0004-medical-record-ownership-and-rls.md).

### Отличия от решения по умолчанию из ТЗ 0.7 (с учётом ревью)

- Строгий вариант (решение ревью): `tenant` недоступен пациенту; добавлены
  классы `tenant-public` и `patient-registry`.
- Шаблоны политик разделены на RESTRICTIVE-инварианты и
  PERMISSIVE-разрешения; тест схемы сверяет точный набор.
- Путь пациента без `system` (решение ревью): субъект `patient_resolve`
  и RESTRICTIVE-политика на карточках.
- Добавлен `app.actor_id`: он нужен аудиту (0014) и разрешению карточек.
- `patient_id` — пациент клиники, а не аккаунт.
- Явный запрет FK между схемами модулей; направление `org` → `iam`.
- Явное ограничение «одна ячейка на пользователя».

## Альтернативы

- **Без политики по субъекту, изоляция пациентов только в коде.** Проще,
  но IDOR в кабинете пациента — одна из самых частых уязвимостей
  медицинских порталов, а цена ошибки — медзапись чужого человека.
- **Разрешение карточки под `system`** (первая редакция этого ADR).
  `system`-транзакция видит всех пациентов клиники, и ошибка в шаге
  разрешения открывала бы чужую карточку. Отклонено на ревью.
- **Мягкий вариант: `tenant`-таблицы доступны и пациенту.** Не нужны
  классы `tenant-public` и `patient-registry`, но неверно
  классифицированная таблица с данными пациентов утекает в кабинет.
  Отклонено на ревью.
- **`patient_id` = `iam.users.id`.** Нет таблицы-карточки и шага
  разрешения. Но исключены пациенты без аккаунта и опекунство, а
  медзапись клиники оказывается привязана к платформенному аккаунту.
- **`app.patient_ids` — массив субъектов в одной транзакции.** Удобно для
  «семейного» экрана, но расширяет видимость одной транзакции. Выбрано
  «одна транзакция — один субъект».
- **Отдельная роль БД на модуль** (`iam_rw`, `org_rw`,
  `SET LOCAL ROLE` на входе в модуль). Это второй рубеж для
  `cell-global` таблиц. Стоит сложности в межмодульных транзакциях.
  Кандидат на усиление, когда появятся чувствительные `cell-global`
  таблицы, кроме `iam`.
- **FK между схемами модулей.** Целостность «бесплатно», но модуль
  перестаёт владеть схемой.

## Последствия

- У `cell-global` таблиц нет второго рубежа в БД: `iam.users` защищает
  только код `iam` и правило «доступ через контракт» (тест архитектуры,
  0012). Это сознательный риск.
- Тест схемы (integration, по `pg_catalog`) делает классификацию
  обязательной: новая таблица без класса, без RLS или с лишней
  политикой не пройдёт CI.
- Кабинет пациента — две транзакции на запрос (разрешение + работа). Их
  можно объединить кешем разрешения на время сессии, если понадобится.
- Часовой пояс клиники — IANA-имя. Бинарник встраивает базу часовых поясов
  (`import _ "time/tzdata"`).
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(a)(1), §164.308(a)(4);
  - GDPR ст. 25, 32;
  - ISO/IEC 27001:2022 A.5.15, A.8.3;
  - SOC 2 CC6.1, CC6.3.

## Открытые вопросы (решаются в ТЗ IAM и модуля пациентов)

- Способ входа: телефон + OTP или email + пароль.
- Собирается ли ИИН при регистрации; хранение и маскирование ИИН.
- Процесс верификации врача (лицензия) и основателя клиники.
- 2FA для персонала.
- Как пациент без аккаунта «забирает» свою карточку.
- Опекунство: кто и как подтверждает связь родитель ↔ ребёнок.
- Доступ поддержки NeuroDent к данным клиники (break-glass): только по
  разрешению клиники, ограниченный по времени, с аудитом. Отдельный ADR.
