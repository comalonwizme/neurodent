# 0020. Transactional outbox

- Статус: Принято (после ревью, 2026-09-28)
- Дата: 2026-09-28
- Связанные: 0003 (резидентность), 0010 (секреты), 0011 (классы таблиц), 0012 (транзакции), 0014 (аудит), 0016 (rate limit), 0019 (push)

## Контекст

По [0012](0012-module-template-and-cross-module-transactions.md) внутри
транзакции нет сетевого I/O: SMS, push, HTTP, AI-сервис. Но многие
действия должны вызвать внешнюю доставку **тогда и только тогда, когда
транзакция зафиксирована**:

- код входа по SMS (IAM, фаза 1);
- напоминание о приёме (SMS и push, фаза 4);
- списание материалов по проведённой процедуре — событие между модулями
  (фаза 6).

Способы, которые не работают:

- **Отправка после коммита в той же горутине или в новой.** Процесс падает
  между коммитом и отправкой — сообщение потеряно, хотя действие
  зафиксировано.
- **Отправка до коммита.** Транзакция откатывается — сообщение ушло о
  том, чего не было.

Для входа по телефону есть ещё одно требование. Снаружи не должно быть
видно, зарегистрирован ли номер. Если бы эндпоинт запроса кода вызывал
SMS-провайдера синхронно, разница в пути выполнения читалась бы по
времени ответа. Постановка в очередь в транзакции делает путь одинаковым.

Первоначально outbox был запланирован на фазу 2. Вход по телефону
переносит его в платформу до IAM.

## Решение

### Таблица `platform.outbox`

| Поле | Тип | Что |
|---|---|---|
| `id` | uuid | `shared/id`; он же ключ идемпотентности для получателя |
| `kind` | text | код `<модуль>.<ресурс>.<глагол>`, формат как в 0014 (`iam.otp.sms_requested`) |
| `tenant_id` | uuid, NULL | из scope транзакции, подставляет БД (`platform.current_tenant_id()`); NULL — вне клиники |
| `payload` | jsonb | несекретная часть: идентификаторы и коды. Не больше 4 КБ (CHECK) |
| `sealed` | bytea, NULL | секретная часть, зашифрованная (ниже) |
| `created_at` | timestamptz | `clock_timestamp()` |
| `available_at` | timestamptz | не раньше этого момента; сдвигается при повторе |
| `expires_at` | timestamptz, NULL | после этого момента не доставлять вовсе |
| `attempts` | int | сколько раз забиралась на доставку |
| `locked_until` | timestamptz, NULL | аренда: пока не истекла, другой диспетчер строку не берёт |
| `status` | text | `pending` или `dead` |
| `last_error` | text, NULL | **код** ошибки из закрытого перечня, не текст |

Почему `last_error` — код. Текст ошибки провайдера может цитировать номер
телефона или содержимое сообщения.

### Что можно класть в сообщение

- **`payload`** — только то, что можно показать в логах: идентификаторы
  (UUID), коды, числа. Для каждого `kind` — свой Go-тип payload,
  объявленный в контракте модуля-производителя. Свободного текста нет,
  как в аудите (0014).
- **Персональные данные и секреты** (номер телефона, код OTP, токен
  устройства для push) — только в `sealed`.
  - AES-256-GCM, nonce 96 бит из CSPRNG.
  - Associated data — `id || kind`: зашифрованную часть нельзя
    переставить в другую строку.
  - Формат: версия (1 байт) || id ключа (1 байт) || nonce || шифртекст
    с тегом.
  - Ключи: `NEURODENT_OUTBOX_SEAL_KEY` (текущий) и необязательный
    `NEURODENT_OUTBOX_SEAL_KEY_PREVIOUS` для ротации. Секреты по 0010,
    ровно 32 байта.
- **PHI в outbox не кладётся никогда**, даже зашифрованным. Обработчик
  получает идентификатор и сам читает данные под нужным scope в момент
  доставки.

Зачем шифровать в своей же БД. Строка живёт секунды или минуты, но
попадает в WAL, бэкапы и реплики. Код OTP в открытом виде в бэкапе —
действующий секрет в течение TTL, а телефон там — лишняя копия
персональных данных.

### Постановка: в транзакции действия

`outbox.Enqueue(ctx, msg)` пишет строку в **текущую** транзакцию из
контекста (0012):

- нет транзакции в контексте — ошибка `ErrNoTx`;
- откат транзакции убирает и сообщение, коммит — фиксирует.

Нет действия без сообщения и сообщения без действия.

### Доставка: диспетчер без сетевого I/O в транзакции

Диспетчер — фоновый цикл, его жизненный цикл в `internal/app` (как
очистка счётчиков в 0016). Работает в scope `Global(System())`.

1. **Забрать пачку** — короткая собственная транзакция:

   ```sql
   UPDATE platform.outbox
      SET locked_until = now() + $lease, attempts = attempts + 1
    WHERE id IN (SELECT id FROM platform.outbox
                  WHERE status = 'pending' AND available_at <= now()
                    AND (locked_until IS NULL OR locked_until < now())
                  ORDER BY available_at
                  LIMIT $batch
                  FOR UPDATE SKIP LOCKED)
   RETURNING …
   ```

   Коммит. Несколько реплик не забирают одну строку одновременно.
2. **Доставить** — вне транзакции. Сообщения с истёкшим `expires_at`
   не доставляются: код OTP после TTL бесполезен.
3. **Отметить** — новая короткая транзакция:
   - успех или истёк срок — строка удаляется;
   - ошибка — `available_at` сдвигается с экспоненциальной паузой и
     случайным разбросом, `locked_until` сбрасывается, пишется код
     ошибки;
   - исчерпан лимит попыток или неизвестный `kind` — `status = 'dead'`,
     `sealed` обнуляется. Секрет не хранится в строке, которую никто не
     доставит.

Гарантии:

- **At-least-once.** Процесс упал после доставки, но до удаления —
  аренда истечёт, и сообщение уйдёт повторно. Обработчики обязаны быть
  идемпотентными: передают `id` получателю как ключ идемпотентности, если
  тот поддерживает. Если нет — дубль допустим. Для SMS с кодом это
  безвредно.
- **Порядок не гарантируется.** Обработчик не может полагаться на то, что
  сообщение A доставлено раньше B.
- **Задержка** — интервал опроса (по умолчанию 1 с). `LISTEN/NOTIFY`
  для мгновенного пробуждения — возможное улучшение, не сейчас.

### Класс таблицы `outbox` и RLS

Новый класс `outbox` в шаблонах 0011, тест схемы сверяет его набор
политик.

- ENABLE + FORCE RLS.
- `outbox_enqueue` — FOR INSERT, WITH CHECK
  `tenant_id IS NOT DISTINCT FROM (SELECT platform.current_tenant_id())`.
  Любой scope может поставить сообщение только от своей клиники.
- `outbox_dispatch` — FOR ALL, USING
  `(SELECT platform.current_actor_kind()) = 'system' AND (SELECT platform.current_tenant_id()) IS NULL`.
  Читать, забирать и удалять сообщения может только диспетчер. Сотрудник
  и пациент видят ноль строк.
- Права прикладной роли: `SELECT, INSERT, UPDATE, DELETE`.

### Наблюдаемость

- В лог: `kind`, `id`, номер попытки, код ошибки. Payload и `sealed` —
  никогда.
- Метрики (с фазой 2): глубина очереди, возраст самого старого
  сообщения, число `dead`. Алерт на рост `dead` и на возраст.
- Строки `dead` удаляются через N дней (по умолчанию 14).

## Альтернативы

- **Горутина после коммита.** Теряет сообщения при падении процесса.
- **Внешний брокер** (NATS, RabbitMQ, Kafka). Правильный инструмент для
  больших потоков, но ещё одна система на ячейку: эксплуатация,
  резервирование, шифрование, аудит. Тот же довод, что против Redis в
  0016. И транзакционность с действием всё равно потребовала бы outbox
  перед брокером.
- **Готовая очередь на Postgres** (River). Проверенный код, повторы,
  планировщик. Но своя схема и свои миграции вне нашего мигратора (0008)
  и правил классов таблиц (0011), аргументы задач в открытом JSON.
  Пересмотреть, если понадобятся отложенные задачи по расписанию в
  больших объёмах (напоминания фазы 4).
- **Держать транзакцию открытой на время доставки** (`FOR UPDATE` без
  аренды). Проще, но это сетевой I/O внутри транзакции: нарушает 0012 и
  держит соединение пула на время ответа провайдера.
- **Хранить код OTP в открытом виде, раз строка живёт недолго.** WAL,
  бэкапы и реплики живут дольше строки.

## Последствия

- Миграция: схема и таблица `platform.outbox`, класс `outbox`, индекс по
  `(status, available_at)`.
- Пакет `platform/outbox`:
  - `Enqueue` — реализация порта в `shared/outbox` для use cases, по
    образцу `shared/audit` (0.7.8);
  - диспетчер;
  - реестр обработчиков по `kind`;
  - шифрование `sealed`.
- Конфиг: `NEURODENT_OUTBOX_SEAL_KEY`, `NEURODENT_OUTBOX_SEAL_KEY_PREVIOUS`,
  интервал опроса, размер пачки, аренда, лимит попыток.
- Тесты:
  - откат транзакции не оставляет строки;
  - `Enqueue` вне транзакции — `ErrNoTx`;
  - падение после забора — сообщение доставляется повторно после аренды;
  - два диспетчера параллельно не доставляют одну строку в пределах
    аренды;
  - в `sealed` в БД нет открытого текста; строка с чужим `id` не
    расшифровывается (AAD);
  - сообщение с истёкшим `expires_at` не доставляется;
  - неизвестный `kind` сразу `dead`, `sealed` обнулён;
  - scope сотрудника и пациента видит ноль строк;
  - сообщение из клиники A нельзя вставить со scope клиники B.
- Мутации:
  - убран `SKIP LOCKED`;
  - AAD не проверяется;
  - `sealed` не обнуляется у `dead`.
- Реализация — этап 0.8 платформы, до IAM 1.1.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(a)(2)(iv) (шифрование), §164.312(c)(1)
    (целостность);
  - ISO/IEC 27001:2022 A.8.24 (криптография), A.8.10 (удаление
    информации), A.8.14 (резервирование и надёжность);
  - SOC 2 CC6.1, A1.2.
