# 0021. IAM: вход по телефону, учётные данные, восстановление

- Статус: Предложено
- Дата: 2026-09-28
- Связанные: 0011 (идентичность), 0014 (аудит), 0016 (rate limit), 0017 (сессии), 0019 (клиентские приложения), 0020 (outbox)

## Контекст

Решения владельца проекта (2026-09-28):

- вход по телефону, как в банковских приложениях: код приходит на любой
  номер, и снаружи не видно, зарегистрирован ли он;
- пароль у всех, у персонала — ещё и TOTP;
- ИИН при регистрации не собирается;
- лестница смены номера — от простого пути к долгому;
- удаление аккаунта внутри приложения.

Этот ADR закрывает открытые вопросы
[0011](0011-identity-clinics-cells-table-classes.md): способ входа, ИИН,
2FA для персонала. Модель сессий — в
[0017](0017-sessions-audiences-transports-handoff.md), здесь — как
сессия появляется.

Угрозы, под которые проектируется вход:

- **Перечисление аккаунтов:** «есть ли у этого номера аккаунт в
  медицинском сервисе» — само по себе утечка.
- **Перебор кодов и паролей.**
- **SMS-накачка:** боты заказывают SMS на дорогие номера за наш счёт.
  SMS-бомбинг чужого человека.
- **SIM-swap и переданные номера.** Оператор выдал номер другому
  человеку, или злоумышленник перевыпустил SIM.
- **Фишинг пароля.**

## Решение

### 1. Факторы

Каждая новая сессия требует **двух доказательств**:

1. **Владение номером** — одноразовый код по SMS.
2. **Знание пароля.**

Персонал (аудитория `clinic`) дополнительно — **TOTP** (0017, п. 5).

Исключения, где SMS не нужен:

- **Handoff** (0017, п. 7): владение уже доказано в приложении-источнике.
- **Привязанное устройство** — позже, вместе с кабинетом пациента.

Запасной путь **email + пароль** требует кода, отправленного на email.
Он заменяет владение номером владением почтой, а не отменяет его.
Иначе пароль стал бы единственным фактором.

### 2. Поток входа и регистрации: один для обоих

```
POST /v1/auth/phone/start   {phone, audience}          → 202 {challenge_id, resend_after}
POST /v1/auth/phone/verify  {challenge_id, code}       → 200 {next: "password" | "register", step_token}
POST /v1/auth/password      {step_token, password}     → сессия (клиника: mfa_at пусто)
POST /v1/auth/register      {step_token, full_name, password, email?} → сессия
```

- **`start` не ищет пользователя.** Он проверяет формат и лимиты,
  создаёт челлендж и ставит SMS в outbox (0020). Путь выполнения
  одинаков для любого номера, поэтому время ответа не зависит от наличия
  аккаунта. Это обеспечено структурой кода, а не выравниванием задержек.
- **Развилка — только после `verify`.** Человек уже доказал, что номер
  его, и ответ «аккаунта нет» ничего не раскрывает постороннему.
- **`step_token`** — одноразовый, TTL 10 минут, хранится хешем. Привязан
  к челленджу, номеру и аудитории. Шаг пропустить нельзя: `password` и
  `register` без действительного `step_token` — 401.
- **Регистрация создаёт аккаунт только после подтверждения номера.**
  Черновиков неподтверждённых аккаунтов нет.
- Все ответы `start` одинаковы по статусу, телу и заголовкам. Любой
  эндпоинт, который отвечает «номер занят», запрещён.

**Email-путь** (`/v1/auth/email/start`) устроен так же. Письмо ставится в
outbox всегда. Обработчик при доставке определяет, есть ли аккаунт с
этим email: если есть — отправляет код, если нет — ничего. Путь запроса
одинаков, решение принимается вне него.

### 3. Одноразовые коды

| Параметр | Значение |
|---|---|
| Формат | 6 цифр, CSPRNG |
| TTL | 5 минут; `expires_at` сообщения в outbox тот же |
| Попытки | 5 на челлендж, затем челлендж сгорает |
| Хранение | HMAC-SHA256 с секретом `NEURODENT_OTP_KEY` от `challenge_id` и кода |
| Сравнение | за постоянное время |

Почему HMAC, а не хеш: 10⁶ вариантов кода перебираются мгновенно.
Сам код в открытом виде живёт только в зашифрованной части сообщения
outbox (0020) до доставки.

Новый запрос кода на тот же номер отменяет предыдущий челлендж.

### 4. Лимиты (поверх 0016, Postgres-лимитер, fail closed)

| Политика | Ключ | Лимит |
|---|---|---|
| `iam.otp.phone.burst` | номер | 1 за 60 с |
| `iam.otp.phone.short` | номер | 3 за 10 мин |
| `iam.otp.phone.day` | номер | 10 за сутки |
| `iam.otp.ip` | IP (/64 для IPv6) | 30 за час — грубо, из-за CGNAT |
| `iam.sms.global` | без частей | суточный бюджет SMS ячейки, из конфига |
| `iam.password.account` | аккаунт | 5 неудач за 15 мин |
| `iam.password.account.day` | аккаунт | 20 неудач за сутки |
| `iam.totp.account` | аккаунт | 5 неудач за 15 мин |

- Растущая пауза между запросами кода получается из нескольких политик на
  один ключ. Интерфейс 0016 не меняется.
- Лимиты по номеру срабатывают одинаково для зарегистрированных и
  незарегистрированных номеров.
- **Страны:** коды отправляются только на префиксы из
  `NEURODENT_OTP_ALLOWED_PREFIXES`, по умолчанию `+77`. Это мобильные
  номера Казахстана; `+7` целиком включил бы и Россию. Это главная
  защита от SMS-накачки.
- **Аварийный выключатель:** при исчерпании `iam.sms.global` отправка
  останавливается, срабатывает алерт.
- Капча после порога по IP — не сейчас; вариант, если накачка начнётся
  в пределах лимитов.

### 5. Пароль

- **Хеш:** argon2id, формат PHC (параметры внутри строки хеша).
  - Начальные параметры: m = 19 MiB, t = 2, p = 1 (минимум OWASP). Итог
    калибруется на прод-железе, цель — 50–100 мс.
  - При входе хеш со старыми параметрами пересчитывается.
  - Число одновременных вычислений ограничено семафором: иначе поток
    попыток входа исчерпает память процесса.
- **Политика** (NIST SP 800-63B, пароль как один из двух факторов):
  - длина от 8 до 128 символов, Unicode нормализуется (NFKC);
  - никаких правил «цифра + спецсимвол + заглавная»;
  - запрет паролей из списка утёкших и частых. Список встроен в бинарник,
    проверка локальная: внешние API (Have I Been Pwned) запрещены;
  - запрет пароля, совпадающего с номером телефона или ФИО.
- Смена пароля отзывает все остальные сессии пользователя.

### 6. TOTP для персонала

- RFC 6238: SHA-1, 6 цифр, шаг 30 с, окно ±1 шаг.
- **Повторное использование кода запрещено:** хранится последний
  принятый шаг.
- Секрет хранится зашифрованным (AES-256-GCM, `NEURODENT_TOTP_KEY`,
  AAD — id пользователя).
- **Подключается обязательно при первом входе** в сессию клиники. Без
  отсрочки: сессия без `mfa_at` видит только эндпоинты подключения и
  ввода TOTP (0017).
- **10 кодов восстановления**, одноразовые, хранятся хешем argon2id.
  Показываются один раз при подключении.
- Passkeys (WebAuthn) для персонала — следующее усиление после пилота.
  Модель сессии (`mfa_at`) для них не меняется.

### 7. Восстановление пароля

- **Пациент:** SMS-код → новый пароль. Отзываются все сессии и
  handoff-коды, уведомление на email и push.
- **Сотрудник:** SMS-код + TOTP или код восстановления → новый пароль.
- **Сотрудник без TOTP и кодов:** администратор клиники сбрасывает его
  TOTP. Пароль администратор не видит и не задаёт. Пользователь
  восстанавливает пароль по SMS и подключает TOTP заново.
- **Основатель без администратора** — через поддержку NeuroDent с
  проверкой личности. Процедура — отдельный ADR (break-glass, 0011).

### 8. Смена номера

| Что есть у человека | Что требуется | Ожидание |
|---|---|---|
| Старый номер работает | пароль + код на старый + код на новый | нет |
| Старого номера нет, есть активная сессия | пароль + свежий вход (0017, п. 5) + код на новый | нет |
| Старого номера и сессий нет, email подтверждён | пароль + код на email + код на новый | 24 ч |
| Есть только пароль | пароль + код на новый | 7 дней |
| Сотрудник | к любому пути добавляется TOTP; с TOTP ожидания нет | — |

Во время ожидания:

- работает старый номер;
- в каждый доступный канал уходит уведомление: SMS на старый номер,
  email, push на устройства с сессиями;
- отмена в один шаг из любого канала отзывает все сессии, кроме той,
  из которой отменили.

После смены отзываются все сессии, кроме текущей. Длительности
настраиваются конфигом.

Интерфейс первым предлагает восстановить SIM у оператора с тем же
номером: в Казахстане это обычно занимает один день по удостоверению
личности.

### 9. Удаление аккаунта

Требование Apple при наличии регистрации в приложении (0019).

- Доступно в обоих приложениях. Требует свежего входа (0017, п. 5).
- **Сразу:** аккаунт деактивирован, все сессии и токены устройств
  удалены.
- **Через 30 дней** (в это время можно отменить через вход):
  - удаляются профиль, учётные данные, email, телефон;
  - строка `iam.users` остаётся без персональных данных, чтобы
    ссылки в журнале аудита оставались целостными;
  - карточки пациента в клиниках отвязываются от аккаунта
    (`user_id = NULL`, 0011). Медкарты клиник хранятся по закону РК,
    удаление аккаунта их не удаляет;
  - членства в клиниках удаляются.
- Основатель, который остаётся единственным владельцем клиники, сначала
  передаёт владение или закрывает клинику. Иначе удаление отклоняется.

### 10. Что при регистрации не собирается

- **ИИН** — его запрашивает клиника, когда он нужен для документов.
  Хранение и маскирование — ADR модуля пациентов.
- **Дата рождения, пол, адрес** — там же, по необходимости.

Регистрация: ФИО, телефон (подтверждён), пароль, email по желанию
(подтверждается отдельно, кодом).

### 11. Карточки пациента, созданные клиникой

Клиника может завести карточку пациента по номеру телефона до того, как
человек зарегистрировался (0011, п. 5). Связь с аккаунтом появляется
только после доказательства владения номером: после входа пациент видит
предложение «клиника X ведёт вашу карточку» и подтверждает его.
Механизм — в ADR модуля пациентов, здесь фиксируется принцип: **карточка
не привязывается к аккаунту без подтверждения владельцем номера**.

### 12. Аудит

События — с первого эндпоинта, без PHI и без номеров:

- `iam.challenge.created`, `iam.challenge.verified`, `iam.challenge.failed`;
- `iam.user.registered`, `iam.session.created`, `iam.session.revoked`;
- `iam.password.changed`, `iam.password.reset`;
- `iam.totp.enrolled`, `iam.totp.reset`;
- `iam.phone.change_requested`, `iam.phone.changed`, `iam.phone.change_cancelled`;
- `iam.user.deletion_requested`, `iam.user.deleted`.

Неудачи пишутся как `outcome = denied` через `audit.Do` (0014).

IP-адрес в событиях входа — нет. Решение из 0014 остаётся открытым до
согласования срока хранения с юристом.

## Альтернативы

- **Вход только по SMS-коду, без пароля.** Удобно, но единственный
  фактор, уязвимый к SIM-swap и переданным номерам. Для доступа к медданным
  это замечание аудитора.
- **Раздельные регистрация и вход с проверкой «номер занят».** Проще, но
  раскрывает, кто пользуется сервисом.
- **Выравнивание времени ответа искусственной задержкой.** Хрупко: любой
  новый запрос в одной ветке ломает равенство. Одинаковый путь
  выполнения надёжнее.
- **bcrypt вместо argon2id.** Проверенный, но не требует памяти и хуже
  держит перебор на GPU. Ограничение длины 72 байта.
- **Проверка утёкших паролей через Have I Been Pwned (k-anonymity).**
  Лучше покрытие, но внешний API из ячейки.
- **SMS как второй фактор персонала.** SMS уже первый фактор. Второй
  должен быть другого рода.
- **Мгновенная смена номера по паролю.** Злоумышленник с паролем
  забирает аккаунт за минуту.

## Последствия

- Таблицы `iam` (все `cell-global`, 0011): пользователи, учётные данные,
  челленджи, step-токены, TOTP и коды восстановления, запросы смены
  номера, сессии и handoff-коды (0017). Схема — в ТЗ 1.0.
- Конфиг:
  - секреты `NEURODENT_OTP_KEY`, `NEURODENT_TOTP_KEY`;
  - `NEURODENT_OTP_ALLOWED_PREFIXES`, суточный бюджет SMS;
  - параметры argon2id;
  - длительности смены номера и удаления.
- Порт SMS-провайдера с fake-адаптером для dev и тестов. Выбор
  казахстанского провайдера не блокирует разработку.
- Тесты, обязательные для вливания:
  - одинаковые ответы `start` для зарегистрированного и нового номера;
  - `start` не обращается к таблице пользователей (тест на
    последовательность запросов);
  - шаг без `step_token` — 401;
  - код сгорает после 5 попыток;
  - номер вне разрешённых префиксов — тот же ответ, SMS не ставится;
  - повторное использование шага TOTP — отказ;
  - смена номера по одному паролю не завершается раньше срока, отмена
    работает;
  - удалённый аккаунт не входит, карточки клиник отвязаны.
- Мутации:
  - `start` ищет пользователя и отвечает иначе;
  - нет лимита попыток на челлендж;
  - хеш кода без секрета;
  - TOTP без защиты от повтора.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(d), §164.308(a)(5)(ii)(D) (управление паролями);
  - ISO/IEC 27001:2022 A.5.17 (аутентификационная информация), A.8.5;
  - ISO/IEC 27701 (минимизация PII);
  - SOC 2 CC6.1, CC6.2.
