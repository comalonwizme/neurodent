# 0015. CORS, защита от CSRF и порядок middleware

- Статус: Предложено
- Дата: 2026-09-27
- Заменяет: [0009](0009-middleware-order.md) (после принятия 0009 получает статус «Заменён 0015»)
- Связанные: 0005 (сессии), 0006 (RFC 9457), 0016 (rate limit)

## Контекст

Продукт на `app.<домен>`, API на `api.<домен>`. Это разные origin, но
один site (одна регистрируемая доменная зона). Cookie-сессия
`SameSite=Lax` ([0005](0005-server-side-sessions.md)) уходит с запросами
`app` → `api`: они same-site. Но браузер отдаст странице ответ, только
если API ответит CORS-заголовками с credentials.

Из «один site» следует и угроза. `SameSite` не защищает от запросов с
**других поддоменов того же сайта**: взломанный `blog.<домен>`,
чужой сервис на поддомене. Сейчас от CSRF защищают:

- **обязательный `Content-Type: application/json` в `DecodeJSON`**:
  форма не отправит JSON без preflight;
- **строгий CORS**: preflight с чужого origin не пройдёт.

Но запрос **без тела** (`POST /sessions/logout`,
`POST /invitations/{id}/accept`) — простой запрос. Браузер отправит его
без preflight, с Lax-cookie, и `DecodeJSON` в нём не вызывается.

Порядок middleware из [0009](0009-middleware-order.md) должен вместить
CORS, защиту от CSRF и rate limit
([0016](0016-rate-limiting-and-trusted-proxies.md)) так, чтобы у любого
ответа, включая ошибки из любого слоя, были `request_id`,
security-заголовки и CORS-заголовки. Без CORS-заголовков браузер не
покажет клиенту даже текст ошибки.

## Решение

### Порядок (снаружи внутрь)

```
RequestID → AccessLog → SecurityHeaders → Recover → CORS → CrossOrigin → RateLimit → BodyLimit → Timeout → routeProblems(mux)
```

| Слой | Почему здесь |
|---|---|
| RequestID | id нужен всем ниже: логам паник, access-логу, телам ошибок |
| AccessLog | снаружи всех, кто пишет ответ сам: видит итоговый статус (403, 413, 429, 500, 503) и полную длительность |
| SecurityHeaders | заголовки ставятся до любого ответа |
| Recover | снаружи всех слоёв с логикой (CORS, CrossOrigin, RateLimit, Timeout); снаружи — только простые обёртки |
| CORS | внутри Recover, но до всех, кто пишет ответ: CORS-заголовки ставятся в общую карту заголовков раньше, чем кто-то ответит (даже 500 от Recover). Preflight отвечает сам, не доходя до хендлера и rate limit |
| CrossOrigin (CSRF) | после CORS: preflight уже отвечен; до RateLimit: отвергнутая подделка не тратит лимит |
| RateLimit (по IP) | до BodyLimit и Timeout: 429 без чтения тела и без goroutine хендлера |
| BodyLimit | до Timeout: 413 по Content-Length без запуска goroutine |
| Timeout | ближе всех к хендлеру: бюджет тратится только на хендлер |
| routeProblems | 404/405 роутера в формате RFC 9457 |

Из [0009](0009-middleware-order.md) в силе остаются:

- свой Timeout с буферизацией вместо `http.TimeoutHandler` (стриминг —
  мимо Timeout);
- access-лог без PII (метод, шаблон маршрута, статус, длительность,
  размер, `request_id`);
- правило для входящего `X-Request-ID` (8–64 символа, `[A-Za-z0-9._-]`).

### CORS

Конфигурация — переменная `NEURODENT_CORS_ALLOWED_ORIGINS`: точный список
origin через запятую.

- Формат каждого элемента — `scheme://host[:port]`, без пути, `*` и
  завершающего `/`. Вне dev — только `https`.
- `null` не допускается никогда.
- Пустой список: в staging и prod — отказ старта; в dev CORS выключен.
  Angular dev-server проксирует API, и в dev запросы same-origin.
- Двухэтапная валидация, как у остальных переменных ([0010](0010-configuration-and-secrets.md)).

Разрешённый origin (точное совпадение с `Origin` запроса) получает на
**любом** ответе:

- `Access-Control-Allow-Origin: <origin>`;
- `Access-Control-Allow-Credentials: true`;
- `Access-Control-Expose-Headers: X-Request-ID, Retry-After` — оба не входят
  в список заголовков, которые браузер показывает скрипту без разрешения.
  Без этого клиент не прочтёт ни id для обращения в поддержку, ни время
  до повтора после 429.

`Vary: Origin` ставится на все ответы, в том числе без CORS-заголовков.
Ответ зависит от `Origin`, и кеш не должен отдать ответ для одного origin
другому.

**Preflight** (`OPTIONS` + `Access-Control-Request-Method`) отвечается
middleware, без хендлера.

- Разрешённый origin, метод и заголовки: `204` и:
  - `Allow-Methods: GET, HEAD, POST, PUT, PATCH, DELETE`;
  - `Allow-Headers` — из списка `Content-Type, X-Request-ID`;
  - `Access-Control-Max-Age: 7200`.

  Почему 2 часа: это потолок Chromium, больше он не кеширует. Preflight
  на каждый запрос удвоил бы задержку. Риск кеша после удаления origin из
  списка закрывает CrossOrigin: он проверяет `Origin` на каждом запросе.
- Чужой origin, метод или заголовок: `403` RFC 9457 **без**
  CORS-заголовков. Браузер заблокирует запрос, а отказ будет виден в
  access-логе.

### Защита от CSRF: `http.CrossOriginProtection` (stdlib, Go 1.25+)

Слой отвергает небезопасные (не GET/HEAD/OPTIONS) браузерные запросы с
чужого origin. Как он определяет, откуда запрос:

- по `Sec-Fetch-Site` (есть во всех браузерах с 2023 года);
- или по сравнению `Origin` с `Host`.

Настройка:

- **доверенные origin — тот же `NEURODENT_CORS_ALLOWED_ORIGINS`**: один
  список для двух слоёв;
- **отказ — `403` RFC 9457** (`code: forbidden`) через `SetDenyHandler`;
- **запросы без `Sec-Fetch-Site` и `Origin`** (мобильное приложение,
  AI-сервис, curl) не браузерные и пропускаются.

Слой закрывает бестелые POST с соседних поддоменов и окно кеша preflight.
Своего кода почти нет, новой зависимости нет.

### Отличия от решения по умолчанию из ТЗ 0.7

- **Добавлен слой CrossOrigin (CSRF) и объяснено, почему CORS его не
  заменяет.**
- **CORS стоит внутри Recover**, а не снаружи. Заголовки всё равно есть
  на 500: Recover пишет в ту же карту заголовков, а паника в логике CORS
  даёт чистый 500, а не обрыв соединения.
- **Место RateLimit зафиксировано здесь же.** Иначе 0016 пришлось бы
  снова заменять таблицу порядка.
- **`Access-Control-Expose-Headers`** для `X-Request-ID` и `Retry-After`.
- **Пустой список origin — ошибка и в staging**, не только в prod.

## Альтернативы

- **CORS самым внешним слоем** (до RequestID). Заголовки на всех ответах
  гарантированы, но preflight не получает `request_id` и не попадает в
  access-лог, а паника в CORS не перехватывается.
- **Отражать любой `Origin` в `Allow-Origin`** («разрешить всё с
  credentials»). Стандартная уязвимость: любой сайт читает ответы API от
  имени пользователя.
- **Шаблоны origin (`https://*.<домен>`).** Удобно для превью-стендов, но
  включает любой будущий поддомен, в том числе чужой или взломанный.
  Превью-стенды — отдельным списком в их окружении.
- **CSRF-токен (double submit) вместо `CrossOriginProtection`.**
  Классическая защита, но это состояние, код на клиенте и ещё одна
  cookie. Fetch Metadata покрывает те же сценарии для поддерживаемых
  браузеров. Токен остаётся вариантом, если понадобится поддержка
  браузеров без `Sec-Fetch-Site` и `Origin` на POST.
- **API на том же origin** (`app.<домен>/api`, reverse proxy): CORS не
  нужен совсем. Решение уровня деплоя. Если оно будет принято, CORS
  останется выключенным (пустой список допустим только в dev, значит
  понадобится явный флаг — пересмотреть этот ADR).

## Последствия

- Тест `TestRouter_ErrorResponsesAreUniform` расширяется: для
  разрешённого origin CORS-заголовки есть на 403, 404, 405, 413, 429,
  500, 503. Добавляются кейсы preflight (разрешённый и чужой origin) и
  CSRF (небезопасный запрос с чужого origin — 403, без
  `Sec-Fetch-Site`/`Origin` — пропускается).
- Preflight в access-логе без маршрута. Его стоит помечать отдельно
  (`route=preflight`), чтобы не путать с 404.
- Для IAM: cookie сессии — host-only на `api.<домен>` с префиксом
  `__Host-` (`Secure`, `Path=/`, без `Domain`). Соседние поддомены не
  смогут её ни прочитать, ни перезаписать.
- Спроектировано по контролям:
  - HIPAA 45 CFR §164.312(c)(1) (целостность: защита от
    несанкционированного изменения), §164.312(b) (аудит без PHI в
    журналах);
  - ISO/IEC 27001:2022 A.8.26 (требования к безопасности приложений),
    A.8.15, A.8.28;
  - SOC 2 CC6.6.
