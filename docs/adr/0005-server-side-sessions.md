# 0005. Серверные сессии вместо JWT

- Статус: Принято
- Дата: 2026-09-27

## Контекст

Пользователи — сотрудники клиник и пациенты, доступ — к PHI. Требования:
мгновенный отзыв доступа (увольнение сотрудника, украденное устройство,
смена роли), выход со всех устройств, минимальная поверхность атаки в
браузере. Реализация — в IAM (после фазы 0); здесь фиксируется модель.

## Решение

- Сессия хранится на сервере. Клиент получает только непрозрачный
  случайный идентификатор (не менее 128 бит из CSPRNG) в cookie
  `HttpOnly; Secure; SameSite=Lax` (или `Strict` для административных
  интерфейсов).
- На сервере хранится хеш идентификатора, а не он сам: утечка таблицы
  сессий не даёт готовых cookie.
- Отзыв — удаление записи; следующий запрос уже не аутентифицирован.
- Срок жизни: скользящий idle-таймаут плюс абсолютный максимум.
- CSRF: `SameSite`, обязательный `Content-Type: application/json` на
  изменяющих запросах (`httpx.DecodeJSON` уже это требует) и строгий CORS.

## Альтернативы

- **JWT (access + refresh).** Stateless-проверка без хранилища, но отзыв до
  истечения срока требует denylist — то есть того же серверного состояния.
  Токен в JS-доступном хранилище крадётся XSS; в cookie — теряется главное
  преимущество. Плюс управление ключами подписи и класс ошибок проверки
  алгоритма (`alg=none`, путаница ключей).
- **PASETO.** Убирает проблемы алгоритмов JWT, но не проблему отзыва.

## Последствия

- Запрос к хранилищу сессий на каждый аутентифицированный запрос; при
  росте нагрузки — кеш с коротким TTL и инвалидацией при отзыве.
- Сессии — данные ячейки (см. [0003](0003-cells-and-data-residency.md)):
  пользователь аутентифицируется в ячейке своей клиники.
- 401 по RFC 9110 требует `WWW-Authenticate`; для cookie-сессий
  стандартной схемы нет — решается при реализации IAM.
- Спроектировано по контролям: HIPAA 45 CFR §164.312(d) (аутентификация),
  §164.312(a)(2)(iii) (автоматическое завершение сеанса); ISO/IEC 27001:2022
  A.8.5 (безопасная аутентификация); SOC 2 CC6.1.
