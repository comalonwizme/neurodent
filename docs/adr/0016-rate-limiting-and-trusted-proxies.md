# 0016. Rate limiting и доверенные прокси

- Статус: Принято (после ревью, 2026-09-27)
- Дата: 2026-09-27
- Связанные: 0006 (RFC 9457), 0010 (конфигурация и секреты), 0012 (транзакции), 0015 (порядок middleware)

## Контекст

IAM будет принимать вход, OTP и регистрацию — классические цели перебора.
Нужны лимиты трёх видов:

- **Анонимные запросы** (вход, регистрация, запрос OTP, публичные данные)
  — единственное, что о клиенте известно, это IP.
- **Аутентифицированные запросы** — клиент известен, лимит должен быть на
  него, а не на адрес. За CGNAT мобильных операторов тысячи абонентов
  выходят в интернет с одного IP. В офисе клиники десятки рабочих мест за
  одним NAT. Лимит по IP для них наказывал бы честных пользователей за
  соседей.
- **Точные лимиты по аккаунту или номеру** для входа и OTP: «5 попыток за
  15 минут», независимо от того, на какую реплику пришёл запрос.

Реплик API несколько, поэтому для точных лимитов счётчик должен быть
общим. Redis ради этого не вводим. Клиентский IP за балансировщиком
приходит в `X-Forwarded-For`, но этот заголовок может подделать клиент.
IP — персональные данные: в логи он не пишется (0015). В хранилище
счётчиков его быть не должно, как и телефонов и email.

## Решение

### Интерфейс

```go
package ratelimit

type Policy struct {
    Name   string        // "anon.ip", "user", "iam.login.phone": часть ключа, в логах
    Limit  int           // сколько запросов
    Window time.Duration // за какое окно
}

type Decision struct {
    Allowed    bool
    RetryAfter time.Duration // > 0, если Allowed == false
}

type Limiter interface {
    Allow(ctx context.Context, p Policy, key Key) (Decision, error)
}
```

**`Key` — только HMAC-SHA256** с секретом `NEURODENT_RATELIMIT_KEY`
(`config.Secret`, не короче 32 байт) от имени политики и частей ключа.
Конструктор `ratelimit.NewKey(secret, policy, parts...)` — единственный
способ получить `Key`. Простой SHA-256 здесь не подходит: пространство
номеров телефонов (~10¹⁰) и IPv4 (2³²) перебирается за секунды, так что
хеш без секрета обратим.

### Две реализации за одним интерфейсом

**`ratelimit.Postgres`** — общий счётчик для точных лимитов (IAM).

- Fixed window: таблица `platform.rate_limit_counters`, класс
  `cell-global`, ключ `(key bytea, window_start)`, счётчик.
- Один `INSERT … ON CONFLICT DO UPDATE SET count = count + 1 RETURNING
  count` атомарен при любой конкуренции: блокировку строки берёт Postgres.
- Счётчик пишется **в собственной транзакции**. Если в контексте есть
  открытая транзакция — `ErrInsideTx` (0012). Откат неудачного входа не
  должен отменять учёт попытки, а вторая транзакция рядом с первой — это
  второе соединение и риск взаимоблокировки при исчерпанном пуле.
- Истёкшие окна удаляет фоновая очистка пачками. Её жизненный цикл — в
  `internal/app`.

**`ratelimit.Memory`** — счётчик в памяти реплики, для грубых лимитов
middleware.

- Та же семантика окна, число ключей ограничено: при переполнении
  вытесняются самые старые окна, так что память не растёт от перебора
  адресов.
- В БД ничего не пишется. Причины:
  - Postgres-счётчик на каждый запрос к API — это запись в БД, которую
    атакующий оплачивает даже отклонёнными запросами. Лимитер стал бы
    усилителем нагрузки на ту самую БД, которую защищает;
  - для грубой защиты точный общий счётчик не нужен: при N репликах
    эффективный лимит ≤ N × лимит;
  - объёмные атаки всё равно отсекаются на границе (балансировщик, WAF).

### Middleware: ключ зависит от того, кто клиент

- **Аутентифицированный запрос** — ключ по **пользователю**, политика
  `user`, `NEURODENT_RATELIMIT_USER_PER_MINUTE`, по умолчанию 600.
  - По пользователю, а не по сессии: несколько открытых сессий не должны
    умножать лимит.
  - Почему 600: экран SPA делает пачку запросов, 10 запросов в секунду в
    среднем на человека — с запасом для честной работы. Превышение —
    скрипт или зациклившийся клиент.
- **Анонимный запрос** (нет сессии или она недействительна) — ключ по
  **IP**, политика `anon.ip`, `NEURODENT_RATELIMIT_ANON_PER_MINUTE`, по
  умолчанию 300.
  - Анонимные эндпоинты — вход, регистрация, OTP, публичные данные.
  - Лимит щедрый из-за CGNAT: грубый IP-лимит лишь останавливает флуд.
    Перебор паролей и кодов останавливают точные лимиты по аккаунту и
    номеру в IAM.
  - Для IPv4 ключ — адрес целиком, **для IPv6 — префикс /64**: абоненту
    обычно выдаётся целая /64, и лимит по одному адресу обходится
    перебором адресов внутри неё.

Кто клиент, определяет middleware аутентификации IAM. В порядке цепочки
(0015) место для него зарезервировано перед RateLimit.

- Middleware лимита получает функцию `Principal(r) (userID, ok)`. До
  появления IAM её нет, и все запросы считаются анонимными.
- Запрос с недействительной сессией проходит поиск сессии в БД до лимита:
  аутентификация должна случиться раньше, чем можно выбрать ключ. Мусорные
  значения cookie отсекаются проверкой формата без запроса к БД.
  Правдоподобные случайные токены стоят одного индексного чтения — как и
  ответ 401. Если это станет проблемой, IAM добавит IP-лимит на неудачные
  поиски сессии.

Общее:

- `/healthz` и `/readyz` исключены по точному пути: kubelet не должен
  получить 429 и снять под с балансировки.
- **Превышение — `429` RFC 9457** (`code: rate_limited`) и `Retry-After` в
  целых секундах (округление вверх, минимум 1).
  - `Retry-After` выставляет `httpx.WriteError` для любой ошибки с методом
    `RetryAfter() time.Duration`. Так лимиты IAM получат заголовок без
    изменения `apperr`.
  - CORS отдаёт `Retry-After` скрипту (0015).
- **Отказ лимитера:**
  - middleware (грубые лимиты) пропускает запрос и пишет ошибку в лог —
    **fail open**;
  - точные лимиты входа и OTP в IAM отказывают — **fail closed**: перебор
    паролей во время сбоя хуже недоступного входа.

### Клиентский IP и доверенные прокси

`NEURODENT_TRUSTED_PROXIES` — список CIDR через запятую, валидируется при
старте. Пустой список — `X-Forwarded-For` не учитывается никогда.

1. Адрес соединения (`RemoteAddr`) не из доверенных — клиент и есть
   `RemoteAddr`, XFF игнорируется целиком.
2. Иначе все записи `X-Forwarded-For` (все заголовки, по порядку)
   читаются **справа налево**: доверенные адреса пропускаются, первый
   недоверенный — клиент.

   Правую часть цепочки дописали наши прокси, левую прислал клиент.
   Доверять можно только правой, поэтому идём справа до первого чужого.
3. Неразбираемая запись — граница доверия: дальше влево не идём, клиентом
   считается последний разобранный адрес справа от неё (доверенный прокси).
   Такое возможно только при ошибке настройки нашего прокси: адрес
   клиента дописывает прокси, и он всегда корректен.

Клиентский IP кладётся в контекст (для лимитов и будущих нужд IAM) и
**нигде не пишется в лог**. `Forwarded` (RFC 7239) не поддерживается:
балансировщики целевых платформ ставят `X-Forwarded-For`. Если появится
прокси только с `Forwarded`, это отдельное изменение.

### Отличия от решения по умолчанию из ТЗ 0.7 (с учётом ревью)

- **IP-лимит только для анонимных запросов, для аутентифицированных —
  лимит по пользователю** (ревью: CGNAT).
- **HMAC с секретом вместо хеша** — хеш без секрета обратим.
- **Грубые лимиты в памяти реплики**, Postgres — для точных лимитов.
- **`ErrInsideTx` для Postgres-лимитера при открытой транзакции** (ревью).
- **IPv6 по /64.**
- **Исключение health-проб.**
- **Явная политика fail open / fail closed.**
- **`Retry-After` через интерфейс ошибки**, без изменения `apperr`.

## Альтернативы

- **Один IP-лимит на все запросы** (первая редакция). Проще, но за CGNAT
  и NAT клиники честные пользователи делят лимит с соседями. Отклонено на
  ревью.
- **Лимит по сессии, а не по пользователю.** Точнее отражает «один
  клиент», но пользователь с десятью сессиями получает десятикратный
  лимит.
- **Грубые лимиты на Postgres** (умолчание ТЗ). Точный общий счётчик, но
  запись в БД на каждый запрос и усиление атаки.
- **Redis.** Правильный инструмент для счётчиков, но ещё одна система на
  ячейку: эксплуатация, резервирование, шифрование, аудит. Для объёма
  точных лимитов (вход и OTP — единицы запросов в секунду) Postgres
  достаточно.
- **GCRA или sliding window вместо fixed window.** Плавнее: fixed window
  допускает до 2 × лимит на стыке окон. Для лимитов входа важнее простота
  и объяснимость («5 попыток за 15 минут»), а стык окон перекрывается
  блокировкой аккаунта в IAM.
- **Лимиты только на балансировщике или WAF.** Нужны в любом случае, но
  лимиты по пользователю и номеру телефона там не выразить.
- **Доверять `X-Forwarded-For` всегда или брать самый левый адрес.**
  Любой клиент подставляет чужой IP и обходит лимит или блокирует
  другого.

## Последствия

- Новые переменные:
  - `NEURODENT_TRUSTED_PROXIES`;
  - `NEURODENT_RATELIMIT_KEY` (секрет);
  - `NEURODENT_RATELIMIT_ANON_PER_MINUTE`;
  - `NEURODENT_RATELIMIT_USER_PER_MINUTE`.
- Миграция: `platform.rate_limit_counters`. Прикладной роли нужны
  `SELECT, INSERT, UPDATE, DELETE`: `RETURNING` требует `SELECT`, очистке
  нужен `DELETE`. Персональных данных в таблице нет.
- Смена `NEURODENT_RATELIMIT_KEY` обнуляет счётчики. Это допустимо, и
  ротация ключа не требует миграции.
- Тесты общие для обеих реализаций (одна таблица кейсов на интерфейс):
  - N goroutine под `-race`, лимит не превышен;
  - `Retry-After` в пределах окна;
  - смена окна сбрасывает счётчик;
  - `ErrInsideTx` у Postgres-реализации.

  Для middleware: ключ по пользователю при наличии principal, по IP без
  него. Для XFF:
  - запрос от недоверенного адреса игнорирует XFF;
  - поддельный левый адрес не становится клиентом;
  - IPv6 /64.
- Спроектировано по контролям:
  - ISO/IEC 27001:2022 A.8.5 (безопасная аутентификация: ограничение
    попыток), A.8.6 (управление мощностями);
  - SOC 2 CC6.6.
