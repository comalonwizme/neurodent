# 0.3 — apperr + httpx

## Что сделано

- `internal/shared/apperr` — ошибка приложения: категория (`Kind`), безопасное
  сообщение для клиента, внутренняя причина только для логов.
- `internal/platform/httpx`:
  - `WriteJSON` — сериализация в память до записи заголовков;
  - `DecodeJSON` — строгий декодер;
  - `StatusOf` — единственное место маппинга ошибка → HTTP-статус;
  - `WriteError` / `WriteProblem` — ответ RFC 9457 (`application/problem+json`)
    с `code` и `request_id`;
  - `WithRequestID` / `RequestID` — ключ контекста (заполнит middleware в 0.4).

## Ключевые решения

**Нулевой `Kind` — `Internal`.** Если кто-то соберёт `&apperr.Error{}` или
забудет категорию, клиент получит 500 без деталей, а не 400 с внутренним
текстом. Ошибка конфигурации ведёт к закрытию информации, а не к утечке.

**Поля `Error` неэкспортируемые, конструкторы возвращают `error`.** Литерал
`Error{Message: cause.Error()}` собрать нельзя, сообщение и причину не перепутать.
`error` вместо `*Error` исключает ловушку типизированного nil
(`var e *Error; return e` → непустой `error`).

**Внешняя категория побеждает.** `KindOf` берёт первую `*Error` в цепочке.
Если сервис обернул `NotFound` репозитория в `Unavailable`, это осознанная
переклассификация.

**5xx: detail всегда общий.** Даже «безопасное» сообщение `Internal` или
`Unavailable` («postgres pool exhausted») раскрывает устройство системы, и
клиенту в нём нечего исправлять. Причина уходит в лог на уровне `error`
вместе с `request_id` — по нему поддержка найдёт запись.

**4xx логируются на `debug`.** В проде (`info`, ниже запрещено) они не
пишутся: статус есть в access-логе, а текст может содержать ввод клиента.

**413 без новой категории.** Превышение лимита — это `Invalid` по смыслу, а
413 — деталь HTTP. `StatusOf` проверяет `*http.MaxBytesError` в цепочке
раньше категории, поэтому неважно, где сработал `MaxBytesReader`: в
middleware (0.4) или в `DecodeJSON`. Для клиента есть `code: "payload_too_large"`.

**`DecodeJSON`: почему каждое правило.**

| Правило | Зачем |
|---|---|
| Content-Type = `application/json` | с cookie-сессиями — защита от CSRF: форма не отправит JSON без preflight |
| `DisallowUnknownFields` | опечатка клиента не превращается в нулевое значение; поле `clinic_id`, которого нет в DTO, не игнорируется молча |
| первый байт `{` | `Decode` молча принимает `null` (dst не меняется) |
| второй `Decode` → `io.EOF` | ровно один объект: `{..} мусор`, `{..}{..}` отклоняются |
| `MaxBytesReader` | лимит памяти; соединение закрывается после ответа |
| тип в терминах JSON | `must be a number`, а не `int64`: не раскрываем Go-типы |
| значения не цитируются | в сообщении имена полей и смещения, но не PHI из тела (есть тест) |

**Unknown field — по тексту ошибки.** В `encoding/json` нет типизированной
ошибки для неизвестного поля. Формат `json: unknown field "x"` стабилен с
Go 1.10 и закреплён тестом: если он изменится, упадёт тест, а не прод.

## Мутации

| Мутация | Упавший тест |
|---|---|
| Убрана замена detail для 5xx | `TestWriteError_ServerErrorHidesDetails` (все 3 подтеста) |
| Отключена проверка хвоста после объекта | `TestDecodeJSON_Rejects/{garbage_after_object,two_objects,extra_closing_brace}` |
| `MaxBytesError` не мапится в 413 | `TestStatusOf/max_bytes*`, `TestDecodeJSON_Rejects/over_limit`, `TestWriteError_PayloadTooLarge` |

## Покрытие

`apperr` 100%, `httpx` 97.5%. Непокрыты только защитные ветки `jsonKind`
(`nil`-тип и экзотические `Kind`) и финальный fallback `decodeError`.

## На что смотреть при ревью

- `WriteProblem` удаляет `ETag`, `Last-Modified` и `Content-Encoding` и ставит
  `Cache-Control: no-store`: ответ об ошибке не должен унаследовать
  кеш-заголовки хендлера.
- `WriteError` — конечная точка: после неё ошибку не возвращают и не логируют.

## Что можно было сделать иначе

- Ошибки валидации по полям (`errors: [{field, message}]`) в problem-ответе.
  Пока не нужны: появятся с первыми DTO в IAM.
- `Retry-After` для 429/503 — поле в `apperr` понадобится вместе с rate limiter.
- 401 по RFC 9110 должен содержать `WWW-Authenticate`. Для cookie-сессий
  стандартной схемы нет; решим в IAM.
- 415 для неверного Content-Type вместо 400. Выбрал 400, чтобы не заводить
  ещё один транспортный особый случай; клиенту важно сообщение, а не код.
